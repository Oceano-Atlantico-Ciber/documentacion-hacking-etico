E3 · Capas, caché y .dockerignore

Un Dockerfile que funciona, pero tarda siempre lo mismo y mete en la imagen lo que no debe. Arréglalo sin cambiar lo que hace.

Qué entregas

En fundamentos/docker/e3/:

FicheroQué lleva
DockerfileEl de preparar.py, reordenado: la instalación de dependencias va antes de copiar app.py, para que salga de la caché. Mismo FROM python:3.12-alpine, mismo CMD ["python", "app.py"] y ningún ENTRYPOINT.
.dockerignoreLo escribes tú: un patrón por línea. Tiene que excluir .env y notas/, que es lo que mira el corrector. Excluir también Dockerfile y .dockerignore es opcional, pero recomendable.
app.pyEl de preparar.py. Puedes cambiar sus comentarios; lo que imprime tiene que seguir siendo cliente de la API listo (requests 2.32.3).
requirements.txtEl de preparar.py, sin cambios: requests==2.32.3.

.env no se sube: tu .gitignore ya lo excluye. notas/ puede subirse o no; lo que cuenta es que no entre en la imagen. Un .dockerignore tiene esta forma (estos patrones son de ejemplo, no los que pide el ejercicio):

*.log
borradores/

1Prepara el escenario

Desde tu repositorio, con Docker Desktop en marcha:

Windows · PowerShell

cd ~/hacking-etico/entregas-<tu-usuario>
py ../documentacion-hacking-etico/00-fundamentos/02-docker/ejercicios/preparar.py e3
cd fundamentos/docker/e3

macOS / Linux · Terminal

cd ~/hacking-etico/entregas-<tu-usuario>
python3 ../documentacion-hacking-etico/00-fundamentos/02-docker/ejercicios/preparar.py e3
cd fundamentos/docker/e3

Deja un cliente de una API: Dockerfile, app.py, requirements.txt, un .env con un token y la carpeta notas/. El .env no aparece en git status: tu .gitignore ya lo excluye. Todas las órdenes que siguen se lanzan desde fundamentos/docker/e3.

2Mira el problema

Construye la imagen tal como está y mira qué tiene dentro (ls y cat corren dentro del contenedor, así que la orden es la misma en todos los sistemas):

docker build -t e3-app:1.0 .
docker run --rm e3-app:1.0 ls -a /app
docker run --rm e3-app:1.0 cat /app/.env

En /app están .env, notas y hasta el Dockerfile, y el segundo docker run imprime API_TOKEN=oa-…: el token y tus notas están dentro de la imagen.

Ahora abre app.py con code app.py, cambia una letra del comentario de la primera línea (# Cliente de la API de la empresa.), guarda y reconstruye:

docker build -t e3-app:1.0 .

El paso RUN pip install se repite entero, aunque requirements.txt no ha cambiado: COPY . . va antes y cualquier cambio en la carpeta obliga a rehacer esa capa.

3Reordena las capas

code Dockerfile

Edita el Dockerfile para que la instalación de dependencias salga de la caché mientras requirements.txt no cambie: copia primero solo ese fichero, instala y copia después app.py. Deja el mismo FROM, el mismo WORKDIR y el mismo CMD, y no añadas ENTRYPOINT.

4Deja fuera lo que no debe entrar

code .dockerignore

El fichero se llama exactamente .dockerignore, con el punto delante y sin extensión. Excluye .env y notas/: es lo obligatorio. Te recomendamos excluir también Dockerfile y .dockerignore, que la imagen no necesita.

5Comprueba antes de subir

Construye una vez con los cambios:

docker build -t e3-app:1.0 .

Cambia otra vez una letra del comentario de app.py, guarda y reconstruye mostrando solo los pasos que salen de la caché:

Windows · PowerShell

cmd /c "docker build --progress=plain -t e3-app:1.0 . 2>&1" | Select-String -Context 1,0 CACHED

macOS / Linux · Terminal

docker build --progress=plain -t e3-app:1.0 . 2>&1 | grep -B1 CACHED

En Windows, cmd /c "… 2>&1" junta en una sola salida todo lo que escribe docker build, para poder filtrarla. Entre lo que sale verás una pareja de líneas parecida a esta, con el mismo número delante (el tuyo puede ser otro):

#8 [4/5] RUN pip install --no-cache-dir -r requirements.txt
#8 CACHED

Por último, mira qué hay en la imagen y que el programa sigue funcionando:

docker run --rm e3-app:1.0 ls -a /app
docker run --rm e3-app:1.0

En /app ya no están .env ni notas. Si excluiste también los otros dos, solo quedan ., .., app.py y requirements.txt. El programa imprime cliente de la API listo (requests 2.32.3).

Qué mira el corrector

El corrector marca fallo si:

  • Falta Dockerfile, .dockerignore, app.py o requirements.txt.
  • Has cambiado requirements.txt o el FROM.
  • La imagen no construye.
  • Has cambiado el CMD o has añadido un ENTRYPOINT.
  • El programa no imprime lo mismo que antes.
  • .env o notas/ están dentro de la imagen.
  • Al cambiar app.py, pip install no sale de la caché.

6Pruébalo en tu equipo

Primero guarda tu trabajo en un commit, desde la raíz de tu repositorio: las pruebas solo ven lo que está en commits.

cd ~/hacking-etico/entregas-<tu-usuario>
git add .
git commit -m "fix(docker-e3): capas en orden y contexto limpio"

Después, con Docker Desktop en marcha, pasa las mismas comprobaciones que el corrector. Trabajan sobre una copia de lo que ya está en commits (la etiqueta, si existe; si no, main) y construyen y levantan contenedores como él.

Windows · PowerShell

cd ~/hacking-etico/entregas-<tu-usuario>
py ../documentacion-hacking-etico/00-fundamentos/02-docker/ejercicios/pruebas.py e3

macOS / Linux · Terminal

cd ~/hacking-etico/entregas-<tu-usuario>
python3 ../documentacion-hacking-etico/00-fundamentos/02-docker/ejercicios/pruebas.py e3

Cada ✗ dice qué falla y por qué. Corrige, haz commit y repite hasta que salga ✓ superado. Antes y después de comprobar, se quitan los contenedores, redes y volúmenes del laboratorio de este ejercicio, para empezar como en un equipo limpio.

7Sube y etiqueta

git push

En la portada de tu repositorio en GitHub, pulsa el ✓ o la ✗ junto al último commit de main y abre Details en Corrector docker. Hay una fila por ejercicio, y se actualiza cuando el docente lanza la corrección. Cuando la fila de E3 salga sin fallos, etiqueta:

git tag -a entrega-fundamentos-docker-e3 -m "E3 resuelto"
git push origin entrega-fundamentos-docker-e3

Si el corrector marca fallos después de etiquetar, corrígelos, súbelos y mueve la etiqueta. El corrector evalúa siempre lo que haya en la etiqueta.
