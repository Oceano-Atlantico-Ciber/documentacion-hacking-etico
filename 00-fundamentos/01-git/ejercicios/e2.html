E2 · .gitignore

Decide qué no debe entrar nunca en el repositorio y deja que git lo ignore por ti.

Teoría
Git 1 · Modelo y commits
Trabajas en
fundamentos/git/e2/
Etiqueta
entrega-fundamentos-git-e2 sobre main

Qué entregas

Un commit en main con estos dos ficheros, y nada más de fundamentos/git/e2/:

FicheroQué lleva
fundamentos/git/e2/app.pyTal como lo deja preparar.py, sin cambios.
fundamentos/git/e2/.gitignoreLas reglas que ignoran build/salida.bin, depuracion.log y .env. Tiene que ignorar los tres él solo: no cuentan el .gitignore de la raíz de tu repositorio ni .git/info/exclude.

build/salida.bin, depuracion.log y .env no pueden estar en ningún commit de la historia, ni siquiera en uno que después los borre. La etiqueta anotada entrega-fundamentos-git-e2 va sobre main, subida a GitHub.

Así se ve una entrega correcta con git log --oneline --name-only -- fundamentos/git/e2 (tu SHA será otro):

6e7f8a9 (HEAD -> main, tag: entrega-fundamentos-git-e2, origin/main) chore(e2): ignorar lo que genera la app
fundamentos/git/e2/.gitignore
fundamentos/git/e2/app.py

1Prepara el escenario

Abre la terminal de VS Code (Terminal → New Terminal; en Windows es PowerShell). Ve a tu repositorio, trae la última versión del material, vuelve a main y mira que no tengas nada a medias. Cambia <tu-usuario> por tu usuario de GitHub:

cd ~/hacking-etico/entregas-<tu-usuario>
git -C ../documentacion-hacking-etico pull
git switch main
git status

git status tiene que terminar en nothing to commit, working tree clean. Si lista ficheros, termina o descarta antes lo que tengas a medias: preparar.py no sigue con cambios pendientes. Después, crea el punto de partida:

Windows · PowerShell

py ../documentacion-hacking-etico/00-fundamentos/01-git/ejercicios/preparar.py e2

macOS / Linux · Terminal

python3 ../documentacion-hacking-etico/00-fundamentos/01-git/ejercicios/preparar.py e2
e2 preparado para <tu-usuario> en fundamentos/git/e2/. Sigue el enunciado.

Deja en fundamentos/git/e2/ el programa app.py y lo que genera al ejecutarse: build/salida.bin, depuracion.log y .env. Mira qué propone subir git:

git status --short -uall fundamentos/git/e2
?? fundamentos/git/e2/app.py
?? fundamentos/git/e2/build/salida.bin
?? fundamentos/git/e2/depuracion.log

.env no aparece porque ya lo ignora el .gitignore de la raíz de tu repositorio. Eso no basta: el de e2/ tiene que ignorarlo también.

Nunca git add . ni git add -A en la raíz del repositorio. Añade cada fichero por su ruta, como en los pasos: un git add . mete en el commit lo de otros ejercicios y lo estropea.

2Escribe el .gitignore

Créalo y escríbelo en VS Code:

code fundamentos/git/e2/.gitignore

Escribe una regla por línea. Las rutas son relativas a la carpeta del .gitignore, e2/, así que no lleven fundamentos/git/e2/ delante. Una carpeta entera se ignora con su nombre y una barra al final:

build/
depuracion.log
.env

Guarda con Ctrl+S (Cmd+S en macOS) y cierra la pestaña.

3Comprueba qué ignora

git status --short -uall fundamentos/git/e2
git check-ignore -v fundamentos/git/e2/build/salida.bin fundamentos/git/e2/depuracion.log fundamentos/git/e2/.env
?? fundamentos/git/e2/.gitignore
?? fundamentos/git/e2/app.py
fundamentos/git/e2/.gitignore:1:build/          fundamentos/git/e2/build/salida.bin
fundamentos/git/e2/.gitignore:2:depuracion.log  fundamentos/git/e2/depuracion.log
fundamentos/git/e2/.gitignore:3:.env            fundamentos/git/e2/.env

La primera orden solo lista .gitignore y app.py. La segunda dice, para cada fichero, qué regla lo ignora y de qué fichero sale: las tres líneas deben empezar por fundamentos/git/e2/.gitignore. Si alguna empieza por .gitignore: (el de la raíz) o no sale, a tu .gitignore le falta esa regla: corrígelo y repite.

4Haz el commit

git add fundamentos/git/e2/app.py fundamentos/git/e2/.gitignore
git commit -m "chore(e2): ignorar lo que genera la app"
[main 6e7f8a9] chore(e2): ignorar lo que genera la app
 2 files changed, 6 insertions(+)
 create mode 100644 fundamentos/git/e2/.gitignore
 create mode 100644 fundamentos/git/e2/app.py

No uses git add -f: se salta el .gitignore.

5Comprueba antes de subir

git log --oneline --name-only -- fundamentos/git/e2

Solo deben aparecer .gitignore y app.py, como en Qué entregas. Si se coló alguno de los otros y todavía no has hecho git push, deshaz el commit, corrige el .gitignore y repite desde el paso 2. Borrarlo con otro commit no sirve: seguiría en la historia.

git reset HEAD~1

El corrector marca fallo si:

  • Falta app.py o su contenido no es el que dejó preparar.py.
  • build/salida.bin, depuracion.log o .env llegaron a algún commit de la historia, aunque después se borraran.
  • Falta fundamentos/git/e2/.gitignore en el commit evaluado.
  • Ese .gitignore, él solo, no ignora alguno de los tres. No cuentan el .gitignore de la raíz, .git/info/exclude ni la configuración de tu equipo.
  • La etiqueta no es anotada: se creó sin -a.

6Pruébalo en tu equipo

pruebas.py pasa las mismas comprobaciones que el corrector, con el mismo código. Evalúa la etiqueta entrega-fundamentos-git-e2 si ya la tienes y, si no, la rama main. Solo mira commits: lo que no esté en un commit no cuenta. No cambia nada de tu repositorio. Desde la carpeta de tu repositorio:

Windows · PowerShell

py ../documentacion-hacking-etico/00-fundamentos/01-git/ejercicios/pruebas.py e2

macOS / Linux · Terminal

python3 ../documentacion-hacking-etico/00-fundamentos/01-git/ejercicios/pruebas.py e2

Antes de subir, un ejercicio bien hecho se ve así (tus SHA serán otros):

E2 · rama main, todavía sin etiqueta (provisional) · 6e7f8a9
  ✓ superado
  ! en GitHub main apunta a 0f9e8d7, no a tu 6e7f8a9: el corrector evaluará el de GitHub. Sube el tuyo (…)
  • ✓ superado: pasa todas las comprobaciones.
  • ✗ es un fallo: el corrector también lo marcará. La línea dice qué ha encontrado y por qué no vale. Corrígelo, haz commit y vuelve a lanzar pruebas.py.
  • ! es un aviso: tu trabajo puede estar bien, pero el corrector evalúa lo que hay en GitHub, no tu equipo, y algo no coincide. Antes de subir es normal ver «aún no está en GitHub» o «en GitHub … apunta a …, no a tu …»: desaparece al subir en el paso siguiente. En ese aviso, el primer SHA es lo que tiene GitHub (lo último que subiste) y el segundo, tu commit.
  • sin empezar: no hay etiqueta ni trabajo en fundamentos/git/e2/ de main: falta preparar el ejercicio o hacer sus commits.
  • Si al final sale Aviso: sin el GitHub CLI con sesión iniciada (gh auth login) no se ha comprobado lo que solo sabe GitHub: el autor de los commits de E1 y el commit filtrado de E8, en este ejercicio no te afecta: todo lo que comprueba el corrector se comprueba también en tu equipo.

7Sube y etiqueta

Sube tu trabajo a GitHub:

git push

Vuelve a lanzar pruebas.py (paso anterior). Cuando diga ✓ superado y no quede ningún aviso ! de GitHub, crea la etiqueta anotada sobre main y súbela:

git tag -a entrega-fundamentos-git-e2 main -m "E2 resuelto"
git push origin entrega-fundamentos-git-e2

Lanza pruebas.py otra vez. Ahora evalúa la etiqueta:

E2 · etiqueta entrega-fundamentos-git-e2 · 6e7f8a9
  ✓ superado

No hay fecha límite: entrega cada ejercicio cuando lo tengas. El progreso de cada alumno se ve en la tabla pública de entregas.

En GitHub, el resultado del corrector está en la portada de tu repositorio: pulsa el ✓ o la ✗ junto al último commit de main y abre Details en Corrector git. Hay una fila por ejercicio: ✅ entregado y superado, ❌ entregado con fallos, ✏️ provisional (aún sin etiqueta) y · sin empezar. Se actualiza cuando el docente lanza la corrección, no en cada push.

Si hay que corregir algo después de etiquetar

  • Al .gitignore le falta una regla: corrígelo con code fundamentos/git/e2/.gitignore, compruébalo como en el paso 3 y haz un commit nuevo solo con él. Eso sí vale: 
    git add fundamentos/git/e2/.gitignore
git commit -m "fix(e2): completar el .gitignore"
git push
  • Se coló en un commit build/salida.bin, depuracion.log o .env: un commit que lo borre no sirve, porque sigue en la historia. Si ese commit es el último y no lo has subido, deshazlo con git reset HEAD~1 y repite desde el paso 2. Si ya está subido (si etiquetaste siguiendo los pasos, es tu caso), no reescribas main: pregunta al docente.

Cuando pruebas.py vuelva a decir ✓ superado sobre la rama, mueve la etiqueta al commit corregido: -f la reemplaza en tu equipo y git push -f, en GitHub (Git 3 · Mover una etiqueta). Haz solo esto, sin tocar commits, si pruebas.py dice que la etiqueta no es anotada o que en GitHub apunta a otro commit:

git tag -fa entrega-fundamentos-git-e2 main -m "E2 resuelto"
git push -f origin entrega-fundamentos-git-e2

Si pruebas.py dice «en GitHub ya existe entrega-fundamentos-git-e2 y no la tienes aquí», la creaste en otro equipo: tráetela con git fetch --tags.
