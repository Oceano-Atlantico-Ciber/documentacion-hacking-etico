E4 · Conflicto

Dos auditores han ampliado el mismo inventario. Une su trabajo y resuelve el conflicto según una regla.

Teoría
Git 2 · Ramas y fusiones
Trabajas en
fundamentos/git/e4/
Etiqueta
entrega-fundamentos-git-e4 sobre main

Qué entregas

main con las ramas git/e4-a y git/e4-b integradas, y el conflicto entre ellas resuelto dentro del merge:

  • Un commit de merge que une las dos ramas: es el que guarda la resolución del conflicto.
  • Los commits feat(e4): puerto encontrado por A y feat(e4): puerto encontrado por B, una vez cada uno.
  • fundamentos/git/e4/puertos.txt según la regla: todas las líneas de las dos ramas, una por puerto, ordenadas por número de puerto de menor a mayor y sin marcadores de conflicto.
  • La etiqueta anotada entrega-fundamentos-git-e4 sobre main, subida a GitHub.

Así se ve una entrega correcta (tus SHA y tus puertos serán otros):

git log --oneline --graph -4
*   8b9c0d1 (HEAD -> main, tag: entrega-fundamentos-git-e4, origin/main) Merge branch 'git/e4-b'
|\
| * 5e6f7a8 (git/e4-b) feat(e4): puerto encontrado por B
* | 3c4d5e6 (git/e4-a) feat(e4): puerto encontrado por A
|/
* 1f2a3b4 feat(e4): inventario de puertos

git show HEAD:fundamentos/git/e4/puertos.txt
21 ftp
143 imap
445 smb
3306 mysql
3389 rdp

1Prepara el escenario

Abre la terminal de VS Code (Terminal → New Terminal; en Windows es PowerShell). Ve a tu repositorio, trae la última versión del material, vuelve a main y mira que no tengas nada a medias. Cambia <tu-usuario> por tu usuario de GitHub:

cd ~/hacking-etico/entregas-<tu-usuario>
git -C ../documentacion-hacking-etico pull
git switch main
git status

git status tiene que terminar en nothing to commit, working tree clean. Si lista ficheros, termina o descarta antes lo que tengas a medias: preparar.py no sigue con cambios pendientes. Después, crea el punto de partida:

Windows · PowerShell

py ../documentacion-hacking-etico/00-fundamentos/01-git/ejercicios/preparar.py e4

macOS / Linux · Terminal

python3 ../documentacion-hacking-etico/00-fundamentos/01-git/ejercicios/preparar.py e4
e4 preparado para <tu-usuario> en fundamentos/git/e4/. Sigue el enunciado.

Añade a main el inventario fundamentos/git/e4/puertos.txt y crea git/e4-a y git/e4-b: cada auditor ha añadido un puerto al final del mismo fichero. Mira qué añade cada uno:

git diff main git/e4-a
git diff main git/e4-b
diff --git a/fundamentos/git/e4/puertos.txt b/fundamentos/git/e4/puertos.txt
…
 143 imap
 445 smb
 3306 mysql
+3389 rdp
diff --git a/fundamentos/git/e4/puertos.txt b/fundamentos/git/e4/puertos.txt
…
 143 imap
 445 smb
 3306 mysql
+21 ftp

La primera salida es la de git/e4-a y la segunda, la de git/e4-b. Las líneas con + son las que añade cada rama: las dos al final del fichero, así que van a chocar. Haz los pasos 2 a 6 seguidos, sin otros commits en main entre medias.

2Fusiona la primera rama

git merge git/e4-a
Updating 1f2a3b4..3c4d5e6
Fast-forward
 fundamentos/git/e4/puertos.txt | 1 +

Entra con fast-forward, como en E3: main no se había movido.

3Fusiona la segunda

git merge git/e4-b
git status
Auto-merging fundamentos/git/e4/puertos.txt
CONFLICT (content): Merge conflict in fundamentos/git/e4/puertos.txt
Automatic merge failed; fix conflicts and then commit the result.
…
Unmerged paths:
        both modified:   fundamentos/git/e4/puertos.txt

Esta da conflicto: las dos ramas cambiaron el mismo sitio del fichero. El merge queda a medias hasta que lo resuelvas. Si te lías, git merge --abort lo cancela y vuelves al principio de este paso.

4Resuelve con la regla

Regla: el inventario final tiene todas las líneas de las dos ramas, una por puerto, ordenadas por número de puerto de menor a mayor (como números: 21 va antes que 143), aunque tengas que mover líneas que ya estaban, y sin marcadores de conflicto.

Abre el fichero:

code fundamentos/git/e4/puertos.txt
143 imap
445 smb
3306 mysql
<<<<<<< HEAD
3389 rdp
=======
21 ftp
>>>>>>> git/e4-b

Entre <<<<<<< HEAD y ======= está lo de tu main (la rama A); entre ======= y >>>>>>>, lo de la rama B. Edita el fichero a mano:

  1. Borra las tres líneas de marcadores: <<<<<<< HEAD, ======= y >>>>>>> git/e4-b.
  2. Deja las dos líneas de puertos, la de A y la de B.
  3. Ordena todas las líneas por número de puerto, aunque tengas que mover líneas que ya estaban: en el ejemplo, 21 ftp sube por encima de 143 imap. Con los puertos del ejemplo queda como en Qué entregas.

Guarda con Ctrl+S (Cmd+S en macOS) y cierra la pestaña.

5Termina el merge

git add fundamentos/git/e4/puertos.txt
git commit --no-edit
[main 8b9c0d1] Merge branch 'git/e4-b'

git add marca el conflicto como resuelto y git commit --no-edit crea el commit de merge con el mensaje que propone git. No lo arregles con un commit aparte ni copiando el fichero: el corrector busca el merge que resolvió el conflicto.

6Comprueba antes de subir

git log --oneline --graph -4
git show HEAD:fundamentos/git/e4/puertos.txt

Un merge con dos padres y el inventario completo y ordenado, como en Qué entregas.

El corrector marca fallo si:

  • Falta el commit feat(e4): puerto encontrado por A o el feat(e4): puerto encontrado por B, o alguno aparece más de una vez.
  • No hay un commit de merge que una una rama con el commit de A y otra con el de B que chocaban entre sí: el conflicto se resuelve dentro de git merge, no copiando el fichero ni con un commit aparte.
  • puertos.txt conserva marcadores de conflicto (<<<<<<<, ======= o >>>>>>>).
  • puertos.txt no sigue la regla: le faltan líneas, le sobran (también repetidas) o no está ordenado por número de puerto.
  • La etiqueta no es anotada: se creó sin -a.

7Pruébalo en tu equipo

pruebas.py pasa las mismas comprobaciones que el corrector, con el mismo código. Evalúa la etiqueta entrega-fundamentos-git-e4 si ya la tienes y, si no, la rama main. Solo mira commits: lo que no esté en un commit no cuenta. No cambia nada de tu repositorio. Desde la carpeta de tu repositorio:

Windows · PowerShell

py ../documentacion-hacking-etico/00-fundamentos/01-git/ejercicios/pruebas.py e4

macOS / Linux · Terminal

python3 ../documentacion-hacking-etico/00-fundamentos/01-git/ejercicios/pruebas.py e4

Antes de subir, un ejercicio bien hecho se ve así (tus SHA serán otros):

E4 · rama main, todavía sin etiqueta (provisional) · 8b9c0d1
  ✓ superado
  ! en GitHub main apunta a 0f9e8d7, no a tu 8b9c0d1: el corrector evaluará el de GitHub. Sube el tuyo (…)
  • ✓ superado: pasa todas las comprobaciones.
  • ✗ es un fallo: el corrector también lo marcará. La línea dice qué ha encontrado y por qué no vale. Corrígelo, haz commit y vuelve a lanzar pruebas.py.
  • ! es un aviso: tu trabajo puede estar bien, pero el corrector evalúa lo que hay en GitHub, no tu equipo, y algo no coincide. Antes de subir es normal ver «aún no está en GitHub» o «en GitHub … apunta a …, no a tu …»: desaparece al subir en el paso siguiente. En ese aviso, el primer SHA es lo que tiene GitHub (lo último que subiste) y el segundo, tu commit.
  • sin empezar: no hay etiqueta ni trabajo en fundamentos/git/e4/ de main: falta preparar el ejercicio o hacer sus commits.
  • Si al final sale Aviso: sin el GitHub CLI con sesión iniciada (gh auth login) no se ha comprobado lo que solo sabe GitHub: el autor de los commits de E1 y el commit filtrado de E8, en este ejercicio no te afecta: todo lo que comprueba el corrector se comprueba también en tu equipo.

8Sube y etiqueta

Sube tu trabajo a GitHub:

git push

Vuelve a lanzar pruebas.py (paso anterior). Cuando diga ✓ superado y no quede ningún aviso ! de GitHub, crea la etiqueta anotada sobre main y súbela:

git tag -a entrega-fundamentos-git-e4 main -m "E4 resuelto"
git push origin entrega-fundamentos-git-e4

Lanza pruebas.py otra vez. Ahora evalúa la etiqueta:

E4 · etiqueta entrega-fundamentos-git-e4 · 8b9c0d1
  ✓ superado

No hay fecha límite: entrega cada ejercicio cuando lo tengas. El progreso de cada alumno se ve en la tabla pública de entregas.

En GitHub, el resultado del corrector está en la portada de tu repositorio: pulsa el ✓ o la ✗ junto al último commit de main y abre Details en Corrector git. Hay una fila por ejercicio: ✅ entregado y superado, ❌ entregado con fallos, ✏️ provisional (aún sin etiqueta) y · sin empezar. Se actualiza cuando el docente lanza la corrección, no en cada push.

Si hay que corregir algo después de etiquetar

  • puertos.txt no sigue la regla, pero el merge que resolvió el conflicto ya está: corrige el fichero con code fundamentos/git/e4/puertos.txt y haz un commit nuevo encima. El merge sigue en la historia y el corrector mira el fichero en la punta de main: 
    git add fundamentos/git/e4/puertos.txt
git commit -m "fix(e4): ordenar el inventario"
git push
  • No hay merge (copiaste el fichero o lo arreglaste con un commit aparte) y ya está subido: no reescribas main; pregunta al docente.

Cuando pruebas.py vuelva a decir ✓ superado sobre la rama, mueve la etiqueta al commit corregido: -f la reemplaza en tu equipo y git push -f, en GitHub (Git 3 · Mover una etiqueta). Haz solo esto, sin tocar commits, si pruebas.py dice que la etiqueta no es anotada o que en GitHub apunta a otro commit:

git tag -fa entrega-fundamentos-git-e4 main -m "E4 resuelto"
git push -f origin entrega-fundamentos-git-e4

Si pruebas.py dice «en GitHub ya existe entrega-fundamentos-git-e4 y no la tienes aquí», la creaste en otro equipo: tráetela con git fetch --tags.
