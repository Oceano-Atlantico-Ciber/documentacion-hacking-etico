REST es HTTP

Una API REST no es una tecnología ni una biblioteca: es HTTP usado con unas reglas. El navegador, curl, Go, Python o Node solo escriben y leen el mismo texto. Este tema enseña a leer y escribir ese texto; los siguientes, a generarlo desde un programa.

Antes: Docker 4Ejercicio: E1 · HTTP a mano

Palabras de este tema

API
La puerta que un programa ofrece a otros programas: qué se le puede pedir y qué contesta.
Cliente
Quien pregunta: el navegador, una app, curl o un script. Siempre empieza él.
Servidor
Quien contesta. Escucha en un puerto y responde a cada petición.
HTTP
El protocolo de la conversación: un texto con un orden fijo, de petición y de respuesta.
Recurso
Cada cosa que maneja la API (una incidencia, sus comentarios), con su propia URL.
REST
Una forma de usar HTTP: recursos con URL propia, el método dice qué se hace y cada petición va sola.
JSON
El formato de texto en que viajan los datos.
Contrato
Lo que la API promete: rutas, métodos, datos y códigos. Lo verás en API 2.

Qué es una API

Piensa en el mostrador de una cafetería: no entras a la cocina, pides en el mostrador con unas palabras acordadas y te devuelven lo que has pedido. Una API es ese mostrador para programas.

Un mismo servidor suele atender a dos tipos de cliente. A una persona con su navegador le devuelve páginas en HTML, pensadas para leerse. A un programa le devuelve datos en JSON, pensados para procesarse. Las dos conversaciones son HTTP.

El viaje de una petición

Cada vez que un cliente necesita algo hace una petición y espera una respuesta. Siempre empieza el cliente: el servidor solo contesta. Recorre el viaje paso a paso.

HTTP: la conversación es texto

Una petición y una respuesta HTTP son texto con un orden fijo. Esta es la petición del viaje anterior y su respuesta, tal como viajan:

GET /api/v1/incidencias/7 HTTP/1.1
Host: localhost:8080
Accept: application/json
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 98

{"id": 7, "titulo": "La VPN se corta", "prioridad": "alta", "estado": "abierta", "tecnico": "sara"}
  • La primera línea de la petición dice qué quieres (GET, leer) y sobre qué (/api/v1/incidencias/7). La de la respuesta, cómo ha ido: 200 OK.
  • Después van las cabeceras, una por línea con la forma Nombre: valor: datos sobre el mensaje.
  • Una línea en blanco separa las cabeceras del cuerpo, los datos. Content-Length dice cuántos bytes ocupa, para que quien lee sepa dónde acaba.
  • Cada línea termina en dos caracteres, \r\n (CRLF). Lo verás al escribir peticiones a mano en el E1.

Con HTTPS el texto es el mismo, pero viaja cifrado. El cifrado protege el viaje; lo que se envía lo sigue decidiendo el cliente.

Míralo en crudo

Con -v, curl enseña la conversación entera: las líneas que empiezan por > son lo que envía y las que empiezan por <, lo que recibe. Con la API del laboratorio del E1 en marcha:

Windows · PowerShell

curl.exe -v http://localhost:8080/api/v1/incidencias/7

macOS / Linux · Terminal

curl -v http://localhost:8080/api/v1/incidencias/7
> GET /api/v1/incidencias/7 HTTP/1.1
> Host: localhost:8080
> User-Agent: curl/8.10.1
> Accept: */*
>
< HTTP/1.1 200 OK
< Server: BaseHTTP/0.6 Python/3.12.8
< Content-Type: application/json
< Content-Length: 98
<
{"id": 7, "titulo": "La VPN se corta", …}

curl ha añadido por su cuenta Host, User-Agent y Accept. Y el servidor ha contado en Server que está hecho con Python: un dato que una API no debería regalar (API 4). En el E1 escribirás tú esas líneas en un fichero y las mandarás con enviar.py, un programa de veinte líneas que abre una conexión y escribe el texto. La respuesta es la misma: no hay magia.

Qué añade REST a HTTP

HTTP ya trae URLs, métodos, códigos y cabeceras. REST solo pide usarlos con criterio. Lo describió Roy Fielding en el año 2000 para explicar por qué la web funciona tan bien, y estas son las reglas que importan para una API:

  1. Cada cosa es un recurso con su URL. Las rutas son nombres, no acciones.
  2. El método dice qué se hace con el recurso: leer, crear, sustituir, cambiar o borrar. Lo ves más abajo.
  3. Cada petición va sola. El servidor no recuerda la anterior: cada una lleva todo lo que hace falta, también quién la envía.
  4. Lo que viaja es una representación del recurso, casi siempre en JSON, con su Content-Type.
  5. El código y las cabeceras dicen cómo ha ido, igual que en cualquier otra respuesta HTTP.
Así síAsí noPor qué
GET /api/v1/incidencias/7GET /api/getIncidencia?id=7La ruta nombra el recurso; leer lo dice el método.
DELETE /api/v1/incidencias/7POST /api/v1/borrarIncidencia/7Borrar ya es un método de HTTP.
/api/v1/incidencias/api/v1/lista-incidenciasLa colección y sus elementos comparten raíz.
/api/v1/incidencias/7/comentarios/api/v1/comentariosDeIncidencia?inc=7Lo que pertenece a un recurso cuelga de su ruta.

Si una API se salta estas reglas sigue siendo HTTP, pero cada cliente tiene que aprender sus manías. Si las cumple, cualquiera que sepa HTTP la entiende sin leer nada más.

JSON: el formato de los datos

Las APIs intercambian los datos en JSON, un texto con seis tipos de valor:

TipoEjemploPara qué
Objeto{"titulo": "Ratón roto", "prioridad": "baja"}Pares clave y valor. Las claves, siempre entre comillas dobles.
Lista[1, 2, 3]Valores en orden.
Texto"abierta"Siempre con comillas dobles.
Número7, 3.5Sin comillas.
Booleanotrue, falseSí o no.
NulonullSin valor, como una incidencia sin técnico.

Una sola coma de más y el servidor rechaza la petición entera. Escribe o pega JSON en la caja; los botones cargan los tres errores más habituales.

Los métodos: qué quieres hacer

La ruta dice sobre qué recurso actúas; el método dice qué haces con él. Cinco métodos cubren casi todo.

MétodoHaceCuerpoRespuesta típica
GETLeerNo200 con los datos
POSTCrearSí201 y la cabecera Location
PUTSustituir enteroSí, el recurso completo200
PATCHCambiar una parteSí, solo lo que cambia200
DELETEBorrarNo204, sin cuerpo

Seguro e idempotente

Un método es seguro si solo lee: llamarlo no cambia nada. Es idempotente si repetirlo una o diez veces deja el servidor igual que hacerlo una vez. Los navegadores, los proxys y las librerías confían en esto: repiten solos una petición idempotente si la red falla, y nunca un POST.

Códigos de estado: cómo ha ido

La primera línea de la respuesta lleva un número de tres cifras. La primera cifra ya dice de quién es el problema.

CódigoNombreCuándo lo responde una API
200OKHa funcionado y la respuesta trae los datos.
201CreatedSe ha creado un recurso; la cabecera Location dice su ruta.
204No ContentHecho, sin nada que devolver.
304Not ModifiedLo que ya tienes sigue valiendo (API 3).
400Bad RequestLa petición no se puede leer: JSON roto, un parámetro sin sentido.
401UnauthorizedNo has dicho quién eres, o la credencial no vale.
403ForbiddenSe sabe quién eres, pero no tienes permiso.
404Not FoundEsa ruta o ese recurso no existe.
405Method Not AllowedLa ruta existe, pero no con ese método. La cabecera Allow dice cuáles sí.
412Precondition FailedEl recurso cambió desde que lo leíste (API 3).
422Unprocessable ContentEl JSON se lee, pero sus datos no valen: falta un campo, sobra otro.
429Too Many RequestsDemasiadas peticiones; Retry-After dice cuánto esperar.
500Internal Server ErrorEl servidor ha fallado. En una API bien hecha, no debería verse nunca.

curl: la petición desde la terminal

curl envía peticiones HTTP desde la terminal. Viene instalado en Windows 10 y 11, en macOS y en casi todas las distribuciones de Linux. En Windows se trabaja en PowerShell y se escribe siempre curl.exe: curl a secas es otra orden de PowerShell (Invoke-WebRequest) que no entiende estas opciones. En macOS y Linux, en la Terminal, es curl. Elige un método, una URL y el cuerpo, y mira cómo se escribe la orden en cada sistema y qué hace cada pieza.

Windows · PowerShell

macOS / Linux · Terminal

    En las dos terminales, todo lo que lleve espacios, comillas dobles, ? o & va entre comillas simples: así la terminal no lo interpreta. En macOS y Linux eso basta para el JSON, '{"prioridad": "alta"}': las simples protegen a las dobles. Windows PowerShell, en cambio, quita las comillas dobles de dentro al pasarle el texto a curl.exe, y la API recibiría {prioridad: alta}, que no es JSON. Por eso en Windows el cuerpo se escribe antes en un fichero con New-Item (en UTF-8, como lo espera la API) y curl.exe lo manda con --data-binary "@cuerpo.json".

    Si la respuesta es un JSON largo, cambia -i por -s (solo el cuerpo, sin cabeceras) y pásala a un programa que la imprima ordenada:

    Windows · PowerShell

    curl.exe -s http://localhost:8080/api/v1/incidencias | ConvertFrom-Json | ConvertTo-Json -Depth 5

    macOS / Linux · Terminal

    curl -s http://localhost:8080/api/v1/incidencias | python3 -m json.tool

    En PowerShell, si las tildes salen mal, ejecuta antes [Console]::OutputEncoding = [Text.Encoding]::UTF8 en esa ventana.

    Del navegador a curl

    Pulsa F12 en cualquier web y ve a la pestaña Network (Red) con el filtro Fetch/XHR: verás cada petición que el JavaScript de la página hace a su API, con su método, su código, sus cabeceras y su cuerpo. Es el mismo texto de este tema.

    F12 → Network→botón derecho en la petición→Copy → Copy as cURL o Copy as PowerShell→pegar en la terminal
    • En macOS y Linux, elige Copy as cURL (en Chrome para Windows y Linux se llama Copy as cURL (bash)) y pégala en la Terminal tal cual.
    • En Windows, ninguna copia de cURL funciona tal cual en PowerShell: la (bash) escribe curl y parte las líneas con \, y la (cmd) usa las comillas de cmd. Elige Copy as PowerShell: es la misma petición, con su método, cabeceras, cookies y cuerpo, escrita con Invoke-WebRequest, y se pega tal cual en PowerShell. Si quieres leerla como curl, copia la (bash) y pégala en el editor, no en la terminal.
    • La orden copiada lleva tus cookies y tus tokens: son tu sesión. No la pegues en una IA en la nube, en un chat ni en tu repositorio sin borrarlos antes.
