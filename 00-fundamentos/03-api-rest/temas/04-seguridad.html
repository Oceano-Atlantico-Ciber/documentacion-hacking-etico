Seguridad

La mayoría de los fallos graves en APIs no son errores raros de un lenguaje: son preguntas que el servidor no se hace. ¿Quién eres? ¿Esto es tuyo? ¿Puedes cambiar este campo? ¿Puedes usar esta función? ¿Cuántas veces lo has intentado? Las respuestas son códigos y cabeceras de HTTP, y se escriben igual en Go, en Python y en Node.

¿Quién eres? Autenticación

Una API REST no recuerda nada entre peticiones, así que cada una tiene que demostrar quién la envía. En el contrato del curso, el cliente cambia usuario y clave por un token una vez y después lo manda en cada petición:

Sin token, o con uno que no existe, la respuesta es 401 con la cabecera WWW-Authenticate: Bearer, que le dice al cliente cómo autenticarse. Una cabecera inventada como X-User: admin no prueba nada: la escribe el cliente. Solo vale lo que el servidor puede comprobar.

La comprobación se escribe una vez y se pone delante de todas las rutas que la necesitan:

// Un envoltorio: comprueba el token y pasa el usuario al manejador por el contexto.
func autenticar(siguiente http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		token, esBearer := strings.CutPrefix(r.Header.Get("Authorization"), "Bearer ")
		u, existe := usuariosPorToken[token]
		if !esBearer || !existe {
			w.Header().Set("WWW-Authenticate", "Bearer")
			problema(w, http.StatusUnauthorized, "Hace falta un token válido")
			return
		}
		siguiente(w, r.WithContext(context.WithValue(r.Context(), claveUsuario, u)))
	}
}

¿Es tuyo? Autorización por objeto

Saber quién eres no basta. Si la ruta es /api/v1/incidencias/7, cualquiera con un token válido puede probar con el 8, el 9 y el 10. Es el fallo número uno de la lista, BOLA (CWE-639): el servidor comprueba que la incidencia existe, pero no de quién es.

Un técnico recibe 404 por la incidencia de otro, igual que por una que no existe: así no confirma ni que existe. La misma comprobación va en la lista (solo las suyas), en PUT, PATCH, DELETE y en los comentarios. Basta con olvidarla en una ruta.

¿Puedes cambiar ese campo? Asignación masiva

Si el servidor copia en el usuario todo lo que llega en el cuerpo, quien sepa cómo se llama el campo del rol se lo cambia (CWE-915):

PATCH /api/v1/usuarios/yo
Authorization: Bearer <token de lucia>

{"nombre": "Lucía", "rol": "admin"}

La defensa es la validación de API 3: una lista de los campos que cada operación acepta. En /api/v1/usuarios/yo, solo nombre; cualquier otro, 422 y nada cambia. Lo mismo con tecnico en una incidencia: un técnico no puede asignársela a otro, y se le responde 403.

¿Puedes usar esa función? Autorización por función

Algunas operaciones son solo de administración: en el contrato del curso, borrar incidencias. Que la web no enseñe el botón no protege nada; la ruta sigue ahí para quien la llame con curl. El servidor comprueba el rol en la propia operación y, si no es admin, responde 403 (BFLA, CWE-285).

¿Cuántas veces? Limitar

Un login que acepta intentos sin fin deja probar claves hasta acertar (CWE-307). En el contrato del curso, tras cinco claves erróneas para un usuario en un minuto, la API responde 429 a ese usuario, aunque la sexta sea buena, con la cabecera Retry-After, que dice los segundos que hay que esperar:

HTTP/1.1 429 Too Many Requests
Retry-After: 41
Content-Type: application/problem+json

{"type": "about:blank", "title": "Too Many Requests", "status": 429,
 "detail": "Demasiados intentos fallidos"}

Lo mismo que el máximo de limit en API 3: cualquier cosa que el cliente pueda pedir sin coste, tiene un límite.

Regla de la IA

Comprobación

  • Distingues autenticación de autorización, y 401 de 403
  • Explicas BOLA, asignación masiva y BFLA con una petición de ejemplo cada uno
  • Sabes dónde se pone la comprobación del token en Go, en FastAPI y en Express
  • Sabes por qué se responde 404 y no 403 a la incidencia de otro
  • Explicas qué hace Retry-After con un 429
  • Quitas de tus respuestas lo que delata el lenguaje o el framework
