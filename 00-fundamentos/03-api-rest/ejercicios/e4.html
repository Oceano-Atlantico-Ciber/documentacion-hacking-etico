Añade a tu API crear, sustituir, cambiar y borrar, con los códigos y las cabeceras que cualquier cliente HTTP espera.

A responder cada escritura como manda HTTP, no como sale de serie.
Buena práctica
201 con Location, 204 sin cuerpo, 405 con Allow, idempotencia.

Qué entregas

La carpeta fundamentos/api/e4/: tu API del E3 con las escrituras añadidas. Cambias el código de tu lenguaje (main.go, main.py o main.js) y, si hace falta, el Dockerfile; lo demás va tal cual lo copia preparar.py. El corrector construye tu imagen y le pasa pruebas.py e3, pruebas.py e4 y unas pocas pruebas más que no ves (abajo dice cuáles).

1Prepara el escenario

En la terminal, cambiando <tu-usuario> por tu usuario de GitHub:

Windows · PowerShell

cd ~/hacking-etico/entregas-<tu-usuario>
py ../documentacion-hacking-etico/00-fundamentos/03-api-rest/ejercicios/preparar.py e4
cd fundamentos/api/e4

macOS / Linux · Terminal

cd ~/hacking-etico/entregas-<tu-usuario>
python3 ../documentacion-hacking-etico/00-fundamentos/03-api-rest/ejercicios/preparar.py e4
cd fundamentos/api/e4

preparar.py copia tu E3 entero a e4/: sigues sobre tu propio código, y el E3 se queda como lo entregaste. No copia node_modules/ ni .venv/: si usas Python o Node, vuelve a instalar las dependencias en la carpeta nueva, como en el paso 1 del E3. Desde ahora arrancas la API desde fundamentos/api/e4/, con las mismas órdenes que en el E3; antes, para la del E3 con Ctrl+C, porque las dos usan el puerto 8000.

2Programa las escrituras

PeticiónResponde
POST /api/v1/incidencias201, la incidencia creada y Location: /api/v1/incidencias/{id}. Si no llegan, estado es abierta y tecnico, null. Sin titulo o prioridad: 400 o 422.
PUT /api/v1/incidencias/{id}200 y la incidencia sustituida entera. Si falta alguno de los cuatro campos: 400 o 422.
PATCH /api/v1/incidencias/{id}200 con solo los campos enviados cambiados.
DELETE /api/v1/incidencias/{id}204 sin cuerpo. Después, esa incidencia da 404.
POST /api/v1/incidencias/{id}/comentarios201, el comentario con su incidencia y Location hacia él.
GET /api/v1/incidencias/{id}/comentarios/{comentario}200 con el comentario, o 404.
Un método que la ruta no tiene405 y Allow con los que sí: GET, POST en la colección; GET, PUT, PATCH, DELETE en un elemento.

Los ids nuevos nunca reutilizan uno existente ni uno borrado. Si a Allow se le añade HEAD u OPTIONS, no pasa nada: las pruebas no los cuentan. Go lo hace solo, con Allow: GET, HEAD, POST en la colección.

FastAPI no lo hace bien de serie. Con la versión de la plantilla (0.115.6), DELETE /api/v1/incidencias responde 405, pero con allow: GET, sin POST: Starlette solo mira la primera ruta que coincide con la URL, y cada método es una ruta distinta. Si programas en Python, el 405 y su Allow completo los tienes que asegurar tú, en la colección y en el elemento.

Para probar una escritura a mano, con tu API arrancada, escribe el cuerpo en un fichero y mándalo con --data-binary: Windows PowerShell quita las comillas dobles de un JSON escrito en la propia orden. Desde fundamentos/api/e4/, la primera orden crea nueva.json, la segunda crea una incidencia y la tercera prueba un método que la colección no tiene:

Windows · PowerShell

New-Item nueva.json -Force -Value '{"titulo": "Impresora atascada (aula 2)", "prioridad": "alta"}'
curl.exe -i -X POST http://localhost:8000/api/v1/incidencias -H "Content-Type: application/json" --data-binary "@nueva.json"
curl.exe -i -X DELETE http://localhost:8000/api/v1/incidencias

macOS / Linux · Terminal

echo '{"titulo": "Impresora atascada (aula 2)", "prioridad": "alta"}' > nueva.json
curl -i -X POST http://localhost:8000/api/v1/incidencias -H "Content-Type: application/json" --data-binary "@nueva.json"
curl -i -X DELETE http://localhost:8000/api/v1/incidencias

Así responde una API que lo hace bien, con el id que toque en tus datos:

HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/v1/incidencias/13

{"id": 13, "titulo": "Impresora atascada (aula 2)", "prioridad": "alta", "estado": "abierta", "tecnico": null}

HTTP/1.1 405 Method Not Allowed
Allow: GET, POST
…

3Pruébalo

Con la API recién arrancada, en otra pestaña de la terminal y desde fundamentos/api/e4/:

Windows · PowerShell

py pruebas.py e4 http://localhost:8000

macOS / Linux · Terminal

python3 pruebas.py e4 http://localhost:8000

Pasa primero las del E3 y después las del E4. Está bien cuando la última línea dice 0 mal. Las pruebas crean y borran: reinicia la API antes de repetirlas, o las del E3 fallarán porque la lista ya no es la de incidencias.json. Cuando salgan todas en ✓, para la API (Ctrl+C), que el contenedor usa el mismo puerto, y pásalas contra el contenedor, con Docker Desktop en marcha:

Windows · PowerShell

docker build -t api-incidencias:e4 .
docker run -d --rm --name api -p 8000:8000 api-incidencias:e4
py pruebas.py e4 http://localhost:8000
docker stop api

macOS / Linux · Terminal

docker build -t api-incidencias:e4 .
docker run -d --rm --name api -p 8000:8000 api-incidencias:e4
python3 pruebas.py e4 http://localhost:8000
docker stop api

El corrector marca fallo si:

  • Alguna prueba de pruebas.py e4 sale en ✗ contra la imagen.
  • Falla alguna de las que no ves: un id borrado reutilizado, un PUT que acepta la mitad de los campos, un DELETE con cuerpo.
