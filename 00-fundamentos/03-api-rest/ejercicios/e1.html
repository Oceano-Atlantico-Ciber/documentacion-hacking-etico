E1 · HTTP a mano

Escribe dos peticiones HTTP en un fichero de texto, mándalas a una API por una conexión sin más y comprueba que recibes lo mismo que con curl.

Teoría
API 1 · REST es HTTP
Aprendes
Que una API REST no es más que texto HTTP, y a leer y escribir ese texto.
Buena práctica
Entender el mensaje antes que la herramienta.

1Prepara el laboratorio

Desde tu repositorio, con Docker Desktop en marcha:

cd ~/hacking-etico/entregas-<tu-usuario>
py ../documentacion-hacking-etico/00-fundamentos/03-api-rest/ejercicios/preparar.py e1
cd fundamentos/api/e1

Construye y arranca la API de incidencias del laboratorio en http://localhost:8080, con datos generados para tu usuario, y deja enviar.py y un LEEME.md que dice cuál es tu incidencia. Comprueba que responde:

curl -i http://localhost:8080/api/v1/incidencias

2Escribe una lectura

code peticion-get.txt

Escribe la petición que lee tu incidencia: la primera línea con el método, la ruta y HTTP/1.1, la cabecera Host: localhost:8080 y una línea en blanco al final. Nada más. Envíala y guarda lo que sale:

py enviar.py peticion-get.txt | tee respuesta-get.txt

enviar.py abre una conexión TCP, escribe el fichero tal cual (solo cambia los saltos de línea por \r\n) y enseña lo que vuelve. Es lo que hace cualquier cliente HTTP.

3Escribe una alta

code peticion-post.txt

Escribe la petición que abre una incidencia nueva con un título tuyo y prioridad baja. Necesita, además de Host, las cabeceras Content-Type: application/json y Content-Length con los bytes exactos del cuerpo, la línea en blanco y el JSON. Una letra con tilde ocupa dos bytes. Envíala:

py enviar.py peticion-post.txt | tee respuesta-post.txt

Tiene que responder 201 Created con la cabecera Location. Si se queda esperando cinco segundos, Content-Length dice más bytes de los que hay; si responde 400, el JSON no está bien o dice menos. Prueba a propósito un Content-Length erróneo para ver qué pasa.

4Lo mismo con curl

curl -v http://localhost:8080/api/v1/incidencias/<tu-incidencia> 2>&1 | tee curl-get.txt
curl -v -X POST http://localhost:8080/api/v1/incidencias -H 'Content-Type: application/json' --data '{"titulo": "…", "prioridad": "baja"}' 2>&1 | tee curl-post.txt

El 2>&1 junta en el fichero lo que curl -v escribe aparte: las líneas > y <.

5Compara

code comparacion.md

Tres apartados cortos, cada uno con su título (## …):

  • Qué añade curl. Las cabeceras que envía curl y no escribiste tú, y para qué sirve cada una.
  • Qué es igual. Por qué la respuesta es la misma con tu fichero y con curl.
  • Qué cuenta el servidor. Qué dice la cabecera Server y por qué no debería decirlo (API 4).

El corrector marca fallo si:

  • peticion-get.txt no es una petición HTTP válida o no lee tu incidencia.
  • peticion-post.txt no crea una incidencia con 201: método, cabeceras, Content-Length o JSON incorrectos.
  • Faltan respuesta-get.txt, respuesta-post.txt, curl-get.txt o curl-post.txt, o no son la salida de esas órdenes.
  • comparacion.md no tiene los tres apartados.

git add .
git commit -m "feat(api-e1): peticiones HTTP escritas a mano"
git push
