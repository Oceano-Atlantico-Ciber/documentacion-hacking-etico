E6 · Errores que ayudan

Haz que tus tres APIs validen lo que reciben y respondan todos los errores en el mismo formato, sin dejar escapar nada de cómo están hechas.

Teoría
API 3 · Buenas prácticas
Aprendes
A validar contra el contrato y a controlar los errores que el framework genera solo.
Buena práctica
400 frente a 422, application/problem+json, ninguna traza.
Trabajas en
fundamentos/api/e6/, con sus tres carpetas de lenguaje
Etiqueta
entrega-fundamentos-api-e6 sobre main

Qué entregas

La carpeta fundamentos/api/e6/ con tus tres APIs (go/, python/ y node/) validando lo que reciben y respondiendo cada error en application/problem+json. Cambias el código de las tres; casos.txt y diferencias.md se suben tal cual. No hay ningún fichero de texto que escribir: lo que se corrige es cómo responden.

Un error bien respondido se ve así; según el caso cambian el código y el detail, pero la forma es siempre la misma:

HTTP/1.1 422 Unprocessable Entity
Content-Type: application/problem+json

{"type": "about:blank", "title": "Unprocessable Entity", "status": 422, "detail": "Falta el campo prioridad"}

status es el mismo número que el código de la respuesta, y detail lo entiende una persona sin decir nada de cómo está hecha la API. title es la frase del código, y cada lenguaje la escribe a su manera: para el 422, Go y Node dicen Unprocessable Entity y Python 3.13, Unprocessable Content, el nombre nuevo de la RFC 9110. Vale cualquiera de las dos. Las pruebas comprueban que title sea un texto, no cuál; el cliente decide por status.

1Prepara el escenario

En la terminal, cambiando <tu-usuario> por tu usuario de GitHub:

Windows · PowerShell

cd ~/hacking-etico/entregas-<tu-usuario>
py ../documentacion-hacking-etico/00-fundamentos/03-api-rest/ejercicios/preparar.py e6
cd fundamentos/api/e6

macOS / Linux · Terminal

cd ~/hacking-etico/entregas-<tu-usuario>
python3 ../documentacion-hacking-etico/00-fundamentos/03-api-rest/ejercicios/preparar.py e6
cd fundamentos/api/e6

preparar.py copia tu E5 a e6/ y añade casos.txt: las peticiones que tus APIs tienen que rechazar, una por línea, con el código que toca a cada una. Por ejemplo, esta línea dice que un POST sin prioridad tiene que dar 422:

POST /api/v1/incidencias | {"titulo": "Falta la prioridad"} | 422

2Antes de tocar nada, mira qué responden hoy

Arranca las tres APIs como en el E5, pero construidas desde e6/: Go en el 8001, Python en el 8002 y Node en el 8003. La primera orden para los contenedores del E5, si siguen en marcha (si no, da un error que puedes ignorar). Desde fundamentos/api/e6/, en cualquier sistema:

docker stop e5-go e5-python e5-node
docker build -t api-e6-go go
docker build -t api-e6-python python
docker build -t api-e6-node node
docker run -d --rm --name e6-go -p 8001:8000 api-e6-go
docker run -d --rm --name e6-python -p 8002:8000 api-e6-python
docker run -d --rm --name e6-node -p 8003:8000 api-e6-node

Es la misma tanda que usarás cada vez que cambies código: docker stop e6-go e6-python e6-node y, después, las órdenes docker build y docker run de arriba.

Prueba a mano unos cuantos casos y fíjate en el código, el Content-Type y el cuerpo. La primera orden escribe en roto.json un cuerpo de una sola línea al que le falta la llave del final; las siguientes lo mandan a las tres APIs y piden a Node una ruta que no existe:

Windows · PowerShell

New-Item roto.json -Force -Value '{"titulo": "Sin cerrar"'
curl.exe -i -X POST http://localhost:8001/api/v1/incidencias -H "Content-Type: application/json" --data-binary "@roto.json"
curl.exe -i -X POST http://localhost:8002/api/v1/incidencias -H "Content-Type: application/json" --data-binary "@roto.json"
curl.exe -i -X POST http://localhost:8003/api/v1/incidencias -H "Content-Type: application/json" --data-binary "@roto.json"
curl.exe -i http://localhost:8003/api/v1/no-existe

macOS / Linux · Terminal

echo '{"titulo": "Sin cerrar"' > roto.json
curl -i -X POST http://localhost:8001/api/v1/incidencias -H "Content-Type: application/json" --data-binary "@roto.json"
curl -i -X POST http://localhost:8002/api/v1/incidencias -H "Content-Type: application/json" --data-binary "@roto.json"
curl -i -X POST http://localhost:8003/api/v1/incidencias -H "Content-Type: application/json" --data-binary "@roto.json"
curl -i http://localhost:8003/api/v1/no-existe

El cuerpo va en un fichero porque Windows PowerShell quita las comillas dobles de un JSON escrito en la propia orden. Para probar otro caso de casos.txt, repite la primera orden con su cuerpo entre las comillas simples y después un curl con su método (-X) y su ruta. Si el cuerpo lleva comillas simples, como ['titulo', 'baja'], escríbelo mejor en el editor: code roto.json, una sola línea, y guarda.

Apunta lo que delata cada una: es justo lo que tienes que cambiar.

3Valida y uniforma los errores

  • Un problema por lenguaje, como en API 3, y todos los errores pasan por él: también el 404 de una ruta que no existe y el 405.
  • 400 si el cuerpo no es JSON; 422 si es JSON pero no vale: no es un objeto, falta un campo obligatorio, sobra un campo que el contrato no tiene, un tipo no cuadra, el título está vacío o pasa de 120 caracteres, la prioridad o el estado no son de la lista, o un comentario está vacío o pasa de 500.
  • Ningún caso acaba en 500, ni lleva trazas, rutas de ficheros o nombres de funciones.

4Pruébalo en las tres

Desde fundamentos/api/e6/, con los tres contenedores recién arrancados:

Windows · PowerShell

py go/pruebas.py e6 http://localhost:8001
py python/pruebas.py e6 http://localhost:8002
py node/pruebas.py e6 http://localhost:8003

macOS / Linux · Terminal

python3 go/pruebas.py e6 http://localhost:8001
python3 python/pruebas.py e6 http://localhost:8002
python3 node/pruebas.py e6 http://localhost:8003

Cada orden pasa también las pruebas del E3 y el E4: validar no puede romper lo que ya funcionaba. Está listo cuando las tres terminan en 0 mal. Reinicia los contenedores entre una pasada y otra. Al final, con los contenedores recién arrancados, comprueba que las tres siguen respondiendo igual:

Windows · PowerShell

py go/pruebas.py e5 http://localhost:8001 http://localhost:8002 http://localhost:8003

macOS / Linux · Terminal

python3 go/pruebas.py e5 http://localhost:8001 http://localhost:8002 http://localhost:8003

El corrector marca fallo si:

  • Algún caso de casos.txt, u otro parecido, no da su código en application/problem+json con type, title, status y detail.
  • Algún error filtra una traza, una ruta de fichero o el nombre de una función.
  • Deja de pasar alguna prueba del E3 o el E4, o las tres APIs dejan de responder igual.
