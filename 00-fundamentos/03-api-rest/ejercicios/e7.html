1Prepara el escenario

En la terminal, cambiando <tu-usuario> por tu usuario de GitHub:

preparar.py copia tu E6 a e7/ y cambia incidencias.json de cada lenguaje por uno con 500 incidencias. Vuelve a construir las tres imágenes para que lleven los datos nuevos y arráncalas como en el E6: Go en el 8001, Python en el 8002 y Node en el 8003. La primera orden para los contenedores del E6, si siguen en marcha. Desde fundamentos/api/e7/, en cualquier sistema:

docker stop e6-go e6-python e6-node
docker build -t api-e7-go go
docker build -t api-e7-python python
docker build -t api-e7-node node
docker run -d --rm --name e7-go -p 8001:8000 api-e7-go
docker run -d --rm --name e7-python -p 8002:8000 api-e7-python
docker run -d --rm --name e7-node -p 8003:8000 api-e7-node

Cada vez que cambies código, docker stop e7-go e7-python e7-node y otra vez las órdenes docker build y docker run.

2Pagina y filtra

  • GET /api/v1/incidencias devuelve como mucho limit incidencias: 20 si no se dice, entre 1 y 100 si se dice.
  • siguiente es el id de la última devuelta, en texto, si quedan más; null si no. Con ?cursor=<ese id> se piden las de id mayor.
  • ?estado= y ?prioridad= filtran, solos o juntos, antes de paginar.
  • Un limit fuera de rango o que no es un número, un cursor que no es un id, o un estado o prioridad que no existen: 400 en problem+json.

3Versiones con ETag

  • Cada incidencia tiene una versión que empieza en 1 y sube con cada PUT o PATCH. Su ETag es ese número entre comillas: "1", "2"…
  • GET de una incidencia, POST, PUT y PATCH devuelven la cabecera ETag.
  • GET con If-None-Match igual al ETag actual: 304 sin cuerpo.
  • PUT, PATCH o DELETE con If-Match distinto del actual: 412 en problem+json, y no se cambia nada.

4Reprodúcelo con dos terminales

Usa una de tus APIs arrancada con los datos recién cargados (aquí la de Go, en el 8001: si ya la has usado, reiníciala con docker stop e7-go y su docker run). Abre dos pestañas de la terminal en fundamentos/api/e7/, una por técnico.

En cualquiera de las dos, prepara tres ficheros de una línea: los dos cuerpos y la cabecera con la versión que las dos leyeron. La cabecera va en un fichero porque Windows PowerShell quitaría las comillas de "1", y el ETag las lleva; así la orden es la misma en todos los sistemas.

Windows · PowerShell

New-Item cerrar.json -Force -Value '{"estado": "cerrada"}'
New-Item prioridad.json -Force -Value '{"prioridad": "media"}'
New-Item version-1.txt -Force -Value 'If-Match: "1"'

macOS / Linux · Terminal

echo '{"estado": "cerrada"}' > cerrar.json
echo '{"prioridad": "media"}' > prioridad.json
echo 'If-Match: "1"' > version-1.txt

Elige una incidencia abierta de tus datos: el escenario es cerrarla. Tu API ya sabe filtrar, así que pídele unas cuantas:

Windows · PowerShell

curl.exe -s "http://localhost:8001/api/v1/incidencias?estado=abierta&limit=3"

macOS / Linux · Terminal

curl -s "http://localhost:8001/api/v1/incidencias?estado=abierta&limit=3"

Quédate con el id de una de ellas. Las órdenes de aquí usan la 4: cambia el 4 por el tuyo en todas.

Las dos pestañas leen esa incidencia y ven su ETag. En cada pestaña:

Windows · PowerShell

curl.exe -i http://localhost:8001/api/v1/incidencias/4

macOS / Linux · Terminal

curl -i http://localhost:8001/api/v1/incidencias/4

La pestaña 1 la cierra con la versión que leyó:

Windows · PowerShell

curl.exe -i -X PATCH http://localhost:8001/api/v1/incidencias/4 -H "Content-Type: application/json" -H "@version-1.txt" --data-binary "@cerrar.json"

macOS / Linux · Terminal

curl -i -X PATCH http://localhost:8001/api/v1/incidencias/4 -H "Content-Type: application/json" -H "@version-1.txt" --data-binary "@cerrar.json"

La pestaña 2, que no se ha enterado, intenta cambiarle la prioridad con la misma versión, que ya es vieja:

Windows · PowerShell

curl.exe -i -X PATCH http://localhost:8001/api/v1/incidencias/4 -H "Content-Type: application/json" -H "@version-1.txt" --data-binary "@prioridad.json"

macOS / Linux · Terminal

curl -i -X PATCH http://localhost:8001/api/v1/incidencias/4 -H "Content-Type: application/json" -H "@version-1.txt" --data-binary "@prioridad.json"

Si tu API lo hace bien, la primera da 200 con ETag: "2" y la segunda, esto:

HTTP/1.1 412 Precondition Failed
Content-Type: application/problem+json
ETag: "2"

{"type": "about:blank", "title": "Precondition Failed", "status": 412, "detail": "La incidencia ya va por la versión 2"}

5Pruébalo en las tres

Desde fundamentos/api/e7/, con los tres contenedores recién arrancados:

Windows · PowerShell

py go/pruebas.py e7 http://localhost:8001
py python/pruebas.py e7 http://localhost:8002
py node/pruebas.py e7 http://localhost:8003
py go/pruebas.py e5 http://localhost:8001 http://localhost:8002 http://localhost:8003

macOS / Linux · Terminal

python3 go/pruebas.py e7 http://localhost:8001
python3 python/pruebas.py e7 http://localhost:8002
python3 node/pruebas.py e7 http://localhost:8003
python3 go/pruebas.py e5 http://localhost:8001 http://localhost:8002 http://localhost:8003

Las cuatro terminan en 0 mal. Reinicia los contenedores antes de la última, porque las pruebas cambian datos: docker stop e7-go e7-python e7-node y sus tres docker run del paso 1.

El corrector marca fallo si:

  • Recorrer la lista con limit y cursor pierde o repite incidencias, o los filtros traen de más o de menos.
  • Un parámetro que no vale no da 400.
  • Falta el ETag, no hay 304 cuando toca o un If-Match antiguo no da 412, o tras el 412 la incidencia ha cambiado.
  • Deja de pasar alguna prueba anterior, o las tres APIs dejan de responder igual.
  • escenario.md no tiene las dos peticiones, sus respuestas y la explicación.
