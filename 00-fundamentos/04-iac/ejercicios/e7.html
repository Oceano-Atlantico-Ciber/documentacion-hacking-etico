1Prepara el ejercicio

Abre la terminal de VS Code (Terminal → New Terminal; en Windows es PowerShell). Ve a tu repositorio, trae la última versión del material y vuelve a main. Cambia <tu-usuario> por tu usuario de GitHub:

cd ~/hacking-etico/entregas-<tu-usuario>
git -C ../documentacion-hacking-etico pull
git switch main

Crea el punto de partida:

Windows · PowerShell

py ../documentacion-hacking-etico/00-fundamentos/04-iac/ejercicios/preparar.py e7

macOS / Linux · Terminal

python3 ../documentacion-hacking-etico/00-fundamentos/04-iac/ejercicios/preparar.py e7
e7 preparado para <tu-usuario> en fundamentos/iac/e7/. Sigue el enunciado.

Deja en e7/empresa/ la misma cuenta del E2 y un LEEME.md con los usuarios y buckets que importan.

2Ten la empresa desplegada

La empresa ya está en tu Floci desde el E2, y quien sabe qué creó Terraform es el estado de e2/empresa/. Esta carpeta nueva empieza sin estado: si lanzaras apply sin más, intentaría crearlo todo otra vez y chocaría con lo que ya existe. Copia el estado del E2 y comprueba que código y cuenta coinciden (con tu Floci en marcha). cp vale igual en PowerShell que en macOS y Linux:

cd fundamentos/iac/e7/empresa
cp ../../e2/empresa/terraform.tfstate .
terraform init
terraform plan
No changes. Your infrastructure matches the configuration.
  • Si el plan quiere crear cosas (to add), es que borraste tu Floci después del E2: lanza terraform apply y escribe yes.
  • Si cp dice que no encuentra el fichero, no tienes el estado del E2. Lanza terraform apply. Si falla con already exists, la empresa está en tu Floci pero nadie sabe que es de este código: empieza con una Floci vacía (docker compose down -v y docker compose up -d en fundamentos/iac/; borra todo lo de la unidad, que ya no necesitas) y repite terraform apply.

El terraform.tfstate copiado no se sube: el .gitignore lo deja fuera.

3Lee el código

code empresa.tf

Lee las dos políticas de IAM, operaciones-todo y becario-trabajo, con la tabla de IaC 4 · Permisos que dan permisos al lado. Fíjate en cada sentencia: qué acciones (Action) y sobre qué recursos (Resource). Los comentarios cuentan lo que el equipo anterior quería hacer; el código, lo que hace de verdad. Mira también qué otros recursos tocan a los usuarios.

4Pregunta a la cuenta

Lo que dice el código hay que comprobarlo en la cuenta. Como administrador (tu configuración por defecto, la clave test), lee lo que hay. Vuelve a e7/, que es donde va simulacion.json, y cambia <huella> por la tuya:

cd ..
aws iam get-user --user-name becario-<huella> --query User.Arn
aws iam get-user-policy --user-name becario-<huella> --policy-name becario-trabajo
aws iam list-access-keys --user-name becario-<huella>

La primera da el ARN del becario, por ejemplo "arn:aws:iam::000000000000:user/becario-1a2b3c4d". Úsalo, sin comillas, donde pone <ARN del becario> (dos veces). Esta orden pregunta a IAM si el becario puede cambiarse sus propios permisos, sin hacerlo, y guarda la respuesta en simulacion.json:

Windows · PowerShell

aws iam simulate-principal-policy --policy-source-arn <ARN del becario> --action-names iam:PutUserPolicy iam:AttachUserPolicy --resource-arns <ARN del becario> > simulacion.json
Get-Content simulacion.json

macOS / Linux · Terminal

aws iam simulate-principal-policy --policy-source-arn <ARN del becario> --action-names iam:PutUserPolicy iam:AttachUserPolicy --resource-arns <ARN del becario> > simulacion.json
cat simulacion.json

La primera orden es una sola línea. No escribe nada en pantalla; la segunda enseña el fichero. Busca el EvalDecision de cada acción: iam:PutUserPolicy tiene que salir allowed. Esa es la prueba del riesgo. Si sale un error en vez de JSON, revisa el ARN y repite la orden: reescribe el fichero.

Ahora el usuario de operaciones y los datos de dirección. Estas no van a ningún fichero (no las guardes en simulacion.json, o perderías la del becario): lee la respuesta en pantalla y apunta lo que veas.

aws iam get-user --user-name operaciones-<huella> --query User.Arn
aws iam get-user-policy --user-name operaciones-<huella> --policy-name operaciones-todo
aws iam simulate-principal-policy --policy-source-arn <ARN de operaciones> --action-names iam:PutUserPolicy iam:CreateAccessKey --resource-arns <ARN de operaciones>
aws iam simulate-principal-policy --policy-source-arn <ARN de operaciones> --action-names s3:GetObject --resource-arns "arn:aws:s3:::secretos-<huella>/*"
aws iam simulate-principal-policy --policy-source-arn <ARN del becario> --action-names s3:GetObject --resource-arns "arn:aws:s3:::secretos-<huella>/*"

5Escribe la auditoría

code auditoria.md

Con la forma de Qué entregas, un apartado por hallazgo de IAM con cuatro respuestas:

  • Dónde está: el recurso de empresa.tf y, si es una política, su nombre y la sentencia (su Sid, si tiene).
  • Fallo: qué está mal configurado y su CWE, de la tabla de IaC 4 · Los fallos de configuración más vistos.
  • Riesgo: qué podría hacer alguien con esa identidad, apoyado en lo que dio la simulación (cita la acción y su EvalDecision).
  • Corrección: cómo se arregla en el código. La harás en el E8.

Como mínimo, tres hallazgos: la política becario-trabajo (nombra la acción iam:PutUserPolicy), la política operaciones-todo y la clave del becario que acabó en un repositorio público. Si ves otros fallos fuera de IAM, añádelos al final en una lista corta. Guarda.

No uses la clave del becario aunque la tengas en la salida becario_clave de Terraform: sería entrar con una identidad que no es tuya. La simulación demuestra lo mismo sin tocar nada.

El corrector marca fallo si:

  • Falta auditoria.md o simulacion.json en e7/.
  • simulacion.json no es la salida JSON de aws iam simulate-principal-policy (por ejemplo, está vacío o tiene un error), o no muestra iam:PutUserPolicy como allowed: simula al becario sobre su propio usuario.
  • auditoria.md no habla de la política becario-trabajo, de la acción iam:PutUserPolicy, de la política operaciones-todo o de la clave del becario.
  • No aparece el CWE-269, o no hay al menos dos CWE distintos.
  • No responde a dónde está, qué riesgo tiene y cómo se corrige (con esas palabras: dónde, riesgo, corrección).

git add fundamentos/iac/e7

pruebas.py pasa las mismas comprobaciones que el corrector, con el mismo código. Evalúa la etiqueta entrega-fundamentos-iac-e7 si ya la tienes y, si no, la rama main. Solo mira commits: lo que no esté en un commit no cuenta. Trabaja sobre una copia y en una Floci nueva y vacía (el contenedor iac-comprobar-floci), así que no cambia nada de tu repositorio ni de tu Floci. Necesita Docker Desktop en marcha. Desde la carpeta de tu repositorio:

Windows · PowerShell

py ../documentacion-hacking-etico/00-fundamentos/04-iac/ejercicios/pruebas.py e7

macOS / Linux · Terminal

python3 ../documentacion-hacking-etico/00-fundamentos/04-iac/ejercicios/pruebas.py e7

En este ejercicio el corrector solo lee simulacion.json y auditoria.md, pero pruebas.py necesita Docker igualmente.

Antes de subir, un ejercicio bien hecho se ve así:

E7 · main, todavía sin etiqueta (provisional) · 7a8b9c0 · comprobando…
  ✓ superado
  ! main aún no está en GitHub: el corrector no lo verá hasta que lo subas
  • ✓ superado: pasa todas las comprobaciones.
  • ✗ es un fallo: el corrector también lo marcará. La línea dice qué ha encontrado y por qué no vale. Corrígelo, haz commit y vuelve a lanzar pruebas.py.
  • ! es un aviso: tu trabajo puede estar bien, pero el corrector evalúa lo que hay en GitHub, no tu equipo, y algo no coincide: «aún no está en GitHub» o «en GitHub … apunta a …, no a tu …». Antes de subir es normal: desaparece al subir en el paso siguiente. Los SHA de tus líneas serán otros.
  • sin empezar: no hay etiqueta ni fundamentos/iac/e7/ en main: falta preparar el ejercicio o hacer su commit.

7Sube y etiqueta

Sube tu trabajo a GitHub:

git push

Vuelve a lanzar pruebas.py (paso anterior). Cuando diga ✓ superado y no quede ningún aviso !, crea la etiqueta anotada sobre main y súbela:

git tag -a entrega-fundamentos-iac-e7 main -m "E7 resuelto"
git push origin entrega-fundamentos-iac-e7

Lanza pruebas.py otra vez. Ahora evalúa la etiqueta:

E7 · etiqueta entrega-fundamentos-iac-e7 · 7a8b9c0 · comprobando…
  ✓ superado

No hay fecha límite: entrega cada ejercicio cuando lo tengas. El progreso de cada alumno se ve en la tabla pública de entregas.

En GitHub, el resultado del corrector está en la portada de tu repositorio: pulsa el ✓ o la ✗ junto al último commit de main y abre Details en Corrector iac. Hay una fila por ejercicio. Se actualiza cuando el docente lanza la corrección, no en cada push.

Si hay que corregir algo después de etiquetar

Corrige en fundamentos/iac/e7/, haz commit y súbelo con git push. Después mueve la etiqueta al commit nuevo: -f la reemplaza en tu equipo y git push -f, en GitHub (Git 3 · Mover una etiqueta). Hasta que la muevas, pruebas.py sigue evaluando la etiqueta antigua. Haz solo esto, sin commits, si pruebas.py marca ✗ la etiqueta no es anotada o avisa de que en GitHub apunta a otro commit:

git tag -fa entrega-fundamentos-iac-e7 main -m "E7 resuelto"
git push -f origin entrega-fundamentos-iac-e7

Si pruebas.py dice que en GitHub ya existe la etiqueta y no la tienes aquí, la creaste en otro equipo: tráetela con git fetch --tags.
