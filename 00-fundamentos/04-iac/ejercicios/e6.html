E6 · Un módulo, dos laboratorios

Convierte tu E5 en un módulo y levanta con él dos laboratorios iguales, cada uno en su red. Es la forma en que se reparten los laboratorios a un grupo: una pieza probada, muchas copias.

entrega-fundamentos-iac-e6 sobre main

Qué entregas

En fundamentos/iac/e6/ de main:

e6/
├── LEEME.md, proveedor.tf    # copiados del E5 por preparar.py, sin cambiar
├── main.tf                   # la raíz: dos bloques module y sus salidas, ningún resource
└── modulos/lab/
    ├── main.tf               # tu laboratorio del E5, con lo que cambia sacado a variables
    ├── variables.tf          # nombre y cidr
    └── outputs.tf            # ip_web

Con apply quedan dos VPC, cada una con su etiqueta Name y su rango, y dentro de cada una un laboratorio que cumple lo mismo que el del E5 (salvo la página, que aquí no se mira: el user_data que viene del E5 puede quedarse como está). La etiqueta anotada entrega-fundamentos-iac-e6 va sobre main, subida a GitHub.

1Prepara el ejercicio

Abre la terminal de VS Code (Terminal → New Terminal; en Windows es PowerShell). Ve a tu repositorio, trae la última versión del material y vuelve a main. Cambia <tu-usuario> por tu usuario de GitHub:

cd ~/hacking-etico/entregas-<tu-usuario>
git -C ../documentacion-hacking-etico pull
git switch main

Crea el punto de partida:

Windows · PowerShell

py ../documentacion-hacking-etico/00-fundamentos/04-iac/ejercicios/preparar.py e6

macOS / Linux · Terminal

python3 ../documentacion-hacking-etico/00-fundamentos/04-iac/ejercicios/preparar.py e6
e6 preparado para <tu-usuario> en fundamentos/iac/e6/. Sigue el enunciado.

preparar.py ha copiado tu E5 en e6/ (no tienes que copiar nada): todos sus ficheros, sin el estado ni .terraform/. Es tu punto de partida. Si el laboratorio del E5 sigue desplegado, no importa: este crea VPC nuevas. Entra en la carpeta:

cd fundamentos/iac/e6

2Mueve el laboratorio a un módulo

Crea la carpeta del módulo y mueve allí tu main.tf. Estas órdenes valen igual en PowerShell que en macOS y Linux:

mkdir modulos
mkdir modulos/lab
mv main.tf modulos/lab/main.tf

Si en el E5 repartiste el laboratorio en varios .tf, muévelos todos menos proveedor.tf, que se queda en la raíz. Ahora el módulo necesita entradas. Crea modulos/lab/variables.tf:

code modulos/lab/variables.tf
variable "nombre" {
  description = "Nombre del laboratorio: va en la etiqueta Name y en lo que tiene que ser único"
  type        = string
}

variable "cidr" {
  description = "Rango de la VPC, por ejemplo 10.1.0.0/16"
  type        = string
}

Aquí no hace falta default: los valores los da la raíz. Abre modulos/lab/main.tf y cambia lo que es distinto en cada laboratorio:

  • En la VPC, cidr_block = var.cidr y tags = { Name = var.nombre }.
  • En las tres subredes, el rango sale del de la VPC: cidr_block = cidrsubnet(var.cidr, 8, 1) para la pública, y 2 y 3 para las privadas.
  • Lo que tiene que ser único en la cuenta lleva el nombre: el identifier de la base de datos ("${var.nombre}-db") y el name de su grupo de subredes ("${var.nombre}-db"). Si no, el segundo laboratorio choca con el primero. Haz lo mismo con el name de los dos grupos de seguridad ("${var.nombre}-web" y "${var.nombre}-db"): así los distingues en la CLI.
  • Quita de aquí el output "ip_web": va en outputs.tf.
code modulos/lab/outputs.tf
output "ip_web" {
  value = aws_instance.web.private_ip
}

Guarda los tres ficheros del módulo.

3Úsalo dos veces

Crea el main.tf de la raíz, en e6/: dos bloques module con nombres y rangos distintos, y una salida con la IP del servidor de cada uno. La raíz no crea ningún recurso por su cuenta.

code main.tf
module "uno" {
  source = "./modulos/lab"
  nombre = "lab-uno"
  cidr   = "10.1.0.0/16"
}

module "dos" {
  source = "./modulos/lab"
  nombre = "lab-dos"
  cidr   = "10.2.0.0/16"
}

output "ip_uno" {
  value = module.uno.ip_web
}

output "ip_dos" {
  value = module.dos.ip_web
}

Guarda, y desde fundamentos/iac/e6/, con tu Floci en marcha:

terraform init
terraform validate
terraform apply
terraform output
aws ec2 describe-vpcs --query "Vpcs[].[CidrBlock,Tags]"

init carga el módulo (Initializing modules...); repítelo cada vez que añadas o cambies un bloque module. apply crea el doble de recursos que en el E5 (escribe yes), y las salidas dan dos IP:

ip_dos = "10.2.1.…"
ip_uno = "10.1.1.…"

En describe-vpcs salen 10.1.0.0/16 con lab-uno y 10.2.0.0/16 con lab-dos, además de la VPC por defecto. Si apply falla con already exists, algún nombre único no lleva var.nombre. Cuando esté bien, destruye (con yes):

terraform destroy

El corrector marca fallo si:

  • Falta proveedor.tf en e6/, o no hay ninguna carpeta dentro de modulos/.
  • Los .tf de la raíz (los de e6/, no los del módulo) no usan un module dos veces, o crean directamente un aws_vpc, un aws_instance o un aws_db_instance.
  • terraform init o apply fallan.
  • No hay al menos dos VPC, o no tienen etiquetas Name distintas, o comparten rango.
  • Algún laboratorio no cumple lo del E5: tres subredes, un servidor con el 80 abierto a todo el mundo y nada más, y una base de datos privada que solo admite al servidor.
  • terraform destroy falla.

4Haz commit y pruébalo

Primero, haz commit. Vuelve a la carpeta del repositorio y mira qué vas a añadir:

cd ~/hacking-etico/entregas-<tu-usuario>
git status --short -uall fundamentos/iac/e6
?? fundamentos/iac/e6/LEEME.md
?? fundamentos/iac/e6/main.tf
?? fundamentos/iac/e6/modulos/lab/main.tf
?? fundamentos/iac/e6/modulos/lab/outputs.tf
?? fundamentos/iac/e6/modulos/lab/variables.tf
?? fundamentos/iac/e6/proveedor.tf

No debe salir ningún terraform.tfstate ni nada de .terraform/: el .gitignore de fundamentos/iac/ los deja fuera, porque el estado puede guardar secretos.

git add fundamentos/iac/e6
git commit -m "feat(iac-e6): módulo lab usado dos veces"

pruebas.py evalúa tu etiqueta entrega-fundamentos-iac-e6, o la rama main si aún no la tienes, con las mismas comprobaciones que el corrector. Solo cuentan los commits: lo que no esté en un commit no se evalúa. Trabaja en una Floci aparte y vacía, así que no toca tu repositorio ni tu Floci.

Necesita Docker Desktop en marcha. Desde la carpeta de tu repositorio:

Windows · PowerShell

py ../documentacion-hacking-etico/00-fundamentos/04-iac/ejercicios/pruebas.py e6

macOS / Linux · Terminal

python3 ../documentacion-hacking-etico/00-fundamentos/04-iac/ejercicios/pruebas.py e6

Este ejercicio crea y destruye un laboratorio entero: cada pruebas.py tarda entre 4 y 8 minutos. Déjalo terminar.

Antes de subir, un ejercicio bien hecho se ve así:

E6 · main, todavía sin etiqueta (provisional) · 7a8b9c0 · comprobando…
  ✓ superado
  ! main aún no está en GitHub: el corrector no lo verá hasta que lo subas
  • ✓ superado: pasa todas las comprobaciones.
  • ✗ es un fallo: el corrector también lo marcará. La línea dice qué ha encontrado y por qué no vale. Corrígelo, haz commit y vuelve a lanzar pruebas.py.
  • ! es un aviso: tu trabajo puede estar bien, pero el corrector evalúa lo que hay en GitHub, no tu equipo, y algo no coincide: «aún no está en GitHub» o «en GitHub … apunta a …, no a tu …». Antes de subir es normal: desaparece al subir en el paso siguiente. Los SHA de tus líneas serán otros.
  • sin empezar: no hay etiqueta ni fundamentos/iac/e6/ en main: falta preparar el ejercicio o hacer su commit.

5Sube y etiqueta

Sube tu trabajo a GitHub:

git push

Vuelve a lanzar pruebas.py (paso anterior). Cuando diga ✓ superado y no quede ningún aviso !, crea la etiqueta anotada sobre main y súbela:

git tag -a entrega-fundamentos-iac-e6 main -m "E6 resuelto"
git push origin entrega-fundamentos-iac-e6

Lanza pruebas.py otra vez. Ahora evalúa la etiqueta:

E6 · etiqueta entrega-fundamentos-iac-e6 · 7a8b9c0 · comprobando…
  ✓ superado

En GitHub, el resultado del corrector está en la portada de tu repositorio: pulsa el ✓ o la ✗ junto al último commit de main y abre Details en Corrector iac. Hay una fila por ejercicio. Se actualiza cuando el docente lanza la corrección, no en cada push.

Si hay que corregir algo después de etiquetar

  • Si has cambiado ficheros: corrige en fundamentos/iac/e6/, haz commit y súbelo con git push. Después mueve la etiqueta al commit nuevo con las dos órdenes de abajo. Hasta que la muevas, pruebas.py sigue evaluando la etiqueta antigua.
  • Si solo falla la etiqueta, porque pruebas.py marca ✗ la etiqueta no es anotada o avisa de que en GitHub apunta a otro commit: muévela, sin hacer ningún commit.

Para mover la etiqueta, -f la reemplaza en tu equipo y git push -f, en GitHub (Git 3 · Mover una etiqueta):

git tag -fa entrega-fundamentos-iac-e6 main -m "E6 resuelto"
git push -f origin entrega-fundamentos-iac-e6

Si pruebas.py dice que en GitHub ya existe la etiqueta y no la tienes aquí, la creaste en otro equipo: tráetela con git fetch --tags.
