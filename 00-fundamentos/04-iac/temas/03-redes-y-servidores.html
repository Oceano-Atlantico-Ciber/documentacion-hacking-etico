Redes y servidores

Un laboratorio típico tiene una red propia, un servidor que se ve desde fuera y una base de datos que solo ve ese servidor. En AWS cada pieza es un recurso, y la seguridad de la red no la da un cortafuegos aparte: está escrita en los propios recursos. Aquí aprendes a escribirlos y a empaquetarlos en un módulo para levantar tantos laboratorios iguales como quieras.

Antes: IaC 2 · TerraformEjercicios: E5 y E6

Palabras de este tema

CIDR
La forma de escribir un rango de direcciones IP: una dirección, una barra y cuántos bits quedan fijos. 10.0.0.0/16 fija los dos primeros números y deja libres los dos últimos: de 10.0.0.0 a 10.0.255.255, 65 536 direcciones. 10.0.1.0/24 fija tres: de 10.0.1.0 a 10.0.1.255, 256.
VPC
Una red privada tuya dentro de la región, con un rango CIDR como 10.0.0.0/16.
Subred
Un trozo del rango de la VPC dentro de una zona de disponibilidad (un centro de datos), como 10.0.1.0/24 en eu-west-1a.
Pública y privada
Una subred es pública si tiene salida a internet por una puerta de enlace (internet gateway); privada si no.
Grupo de seguridad
El cortafuegos de cada servidor o base de datos: reglas de entrada (ingress) y de salida (egress).
AMI
La imagen de disco con la que arranca un servidor EC2: un Ubuntu, un Debian…
Módulo
Una carpeta de Terraform que se usa como una pieza, con sus variables de entrada y sus salidas.

La forma de un laboratorio

Red: VPC y subredes

resource "aws_vpc" "lab" {
  cidr_block = "10.0.0.0/16"
  tags       = { Name = "lab-1a2b3c4d" }
}

resource "aws_subnet" "publica" {
  vpc_id                  = aws_vpc.lab.id
  cidr_block              = "10.0.1.0/24"
  availability_zone       = "eu-west-1a"
  map_public_ip_on_launch = true
}

resource "aws_subnet" "privada_a" {
  vpc_id            = aws_vpc.lab.id
  cidr_block        = "10.0.2.0/24"
  availability_zone = "eu-west-1a"
}

resource "aws_subnet" "privada_b" {
  vpc_id            = aws_vpc.lab.id
  cidr_block        = "10.0.3.0/24"
  availability_zone = "eu-west-1b"
}

Cada subred dice a qué VPC pertenece (vpc_id) y qué trozo de su rango usa. La etiqueta Name es la que muestra la consola de AWS y la que usarás para encontrar tus recursos con la CLI.

Los rangos de las subredes también se pueden calcular. cidrsubnet("10.0.0.0/16", 8, 1) parte el rango de la VPC en trozos de /24 (16 + 8 bits fijos) y te da el trozo número 1: 10.0.1.0/24. Con 2 da 10.0.2.0/24, y así. Es útil cuando el rango de la VPC es una variable.

map_public_ip_on_launch = true da una IP pública a cada servidor que arranca en esa subred. Eso solo no la hace pública: en AWS real hacen falta además una puerta de enlace (aws_internet_gateway) y una tabla de rutas que lleve el tráfico hacia ella. En Floci no hay internet de verdad, así que en esta unidad no las necesitas: la subred pública es la que reservas para lo que se verá desde fuera.

Grupos de seguridad

Un grupo de seguridad deniega todo lo que no permite. Cada regla de entrada dice un protocolo, un rango de puertos y desde dónde: un rango de direcciones o otro grupo de seguridad. Esto último es lo más útil: «la base de datos admite el 5432 desde los servidores que lleven el grupo web», sin escribir ninguna IP.

resource "aws_security_group" "web" {
  name   = "web"
  vpc_id = aws_vpc.lab.id
  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]          # desde cualquier sitio
  }
}

resource "aws_security_group" "db" {
  name   = "db"
  vpc_id = aws_vpc.lab.id
  ingress {
    from_port       = 5432
    to_port         = 5432
    protocol        = "tcp"
    security_groups = [aws_security_group.web.id]   # solo desde el grupo web
  }
}

Cada grupo lleva vpc_id: sin él, AWS lo crea en la VPC por defecto de la cuenta y no protege nada de tu laboratorio. El nombre (name) solo tiene que ser único dentro de la VPC. Los grupos recuerdan las conexiones: si entra una petición al 80, su respuesta sale aunque no haya regla de salida. Lo que más se ve en auditorías es 0.0.0.0/0 en puertos de administración: SSH (22), escritorio remoto (3389) o la propia base de datos.

Servidores y bases de datos

resource "aws_instance" "web" {
  ami                    = "ami-ubuntu2204"
  instance_type          = "t3.micro"
  subnet_id              = aws_subnet.publica.id
  vpc_security_group_ids = [aws_security_group.web.id]
  user_data              = <<-SH
    #!/bin/sh
    echo "Hola" > /usr/share/nginx/html/index.html
  SH
}

resource "random_password" "db" {               # una contraseña generada, que nadie escribe
  length  = 20
  special = false
}

resource "aws_db_subnet_group" "db" {
  name       = "lab-db"
  subnet_ids = [aws_subnet.privada_a.id, aws_subnet.privada_b.id]
}

resource "aws_db_instance" "db" {
  identifier             = "lab-db"
  engine                 = "postgres"
  engine_version         = "16"
  instance_class         = "db.t3.micro"
  allocated_storage      = 20
  username               = "lab"
  password               = random_password.db.result
  db_subnet_group_name   = aws_db_subnet_group.db.name
  vpc_security_group_ids = [aws_security_group.db.id]
  publicly_accessible    = false
  skip_final_snapshot    = true
}

output "ip_web" {
  value = aws_instance.web.private_ip
}

Pieza a pieza:

  • El servidor (aws_instance). instance_type es su tamaño: t3.micro es de los más pequeños, con 2 CPU virtuales y 1 GB de memoria. ami-ubuntu2204 es un nombre de imagen que entiende Floci; en AWS real las AMI tienen identificadores como ami-0abc…, distintos en cada región.
  • El script de arranque (user_data). El servidor lo ejecuta la primera vez que arranca: así se instala y configura sin entrar en él. <<-SH abre un texto de varias líneas, que termina en la línea SH; el guion permite sangrarlo. Lo puede leer cualquiera con permiso para describir la instancia, así que nunca lleva contraseñas.
  • La contraseña de la base de datos tampoco se escribe en el código. random_password (del proveedor hashicorp/random, que terraform init descarga solo) la genera en el primer apply y la guarda en el estado, que no se sube.
  • El grupo de subredes (aws_db_subnet_group). Una base de datos RDS no se coloca en una subred, sino en un grupo de subredes: la lista de subredes donde AWS puede ponerla. Debe tener subredes de al menos dos zonas distintas.
  • La base de datos (aws_db_instance). db.t3.micro es su tamaño, de los más pequeños. publicly_accessible = false impide que tenga una dirección pública. skip_final_snapshot = true deja borrarla sin hacer antes una copia final; sin él, terraform destroy falla porque pide un nombre para esa copia. En un laboratorio es lo que quieres; en una base con datos reales, no.
  • La salida ip_web da la IP privada del servidor, la que tiene siempre. En AWS real, para llegar desde internet usarías public_ip.

En la Floci del curso, los servidores y bases de datos están simulados: terraform apply los crea con toda su configuración y la CLI los describe, pero no arranca ningún Ubuntu ni ningún PostgreSQL. Por eso los compruebas con aws ec2 describe-instances y aws rds describe-db-instances, no entrando en ellos.

Para revisar lo que has creado (cambia vpc-… por el VpcId que da la primera orden):

aws ec2 describe-vpcs --query "Vpcs[].[VpcId,CidrBlock]"
aws ec2 describe-security-groups --filters "Name=vpc-id,Values=vpc-…" --query "SecurityGroups[].[GroupName,IpPermissions]"
aws ec2 describe-instances --query "Reservations[].Instances[].[InstanceId,PrivateIpAddress]"
aws rds describe-db-instances --query "DBInstances[].[DBInstanceIdentifier,PubliclyAccessible]"

Módulos: el mismo laboratorio, muchas veces

Si el laboratorio funciona, quieres otro igual para el compañero, o uno por grupo. Copiar la carpeta duplica también los errores. Un módulo es la carpeta del laboratorio con variables para lo que cambia, y se usa desde otra carpeta, la raíz:

e6/
├── proveedor.tf
├── main.tf                 # la raíz: usa el módulo dos veces
└── modulos/lab/
    ├── variables.tf        # nombre, cidr…
    ├── main.tf             # la VPC, las subredes, los grupos, el servidor y la base
    └── outputs.tf          # lo que devuelve: la IP del servidor…
# modulos/lab/variables.tf
variable "nombre" {
  type = string
}

variable "cidr" {
  type = string
}

# modulos/lab/outputs.tf
output "ip_web" {
  value = aws_instance.web.private_ip
}
# main.tf de la raíz
module "uno" {
  source = "./modulos/lab"
  nombre = "lab-uno"
  cidr   = "10.1.0.0/16"
}

module "dos" {
  source = "./modulos/lab"
  nombre = "lab-dos"
  cidr   = "10.2.0.0/16"
}

output "ip_uno" {
  value = module.uno.ip_web
}

Dentro del módulo todo lo que cambia viene de var.; fuera solo se ven sus salidas (module.uno.ip_web es la salida ip_web del outputs.tf del módulo). Lo que tiene que ser único en la cuenta, como el identifier de la base de datos o el nombre de su grupo de subredes, se construye con la variable: "${var.nombre}-db"; si no, el segundo laboratorio choca con el primero. Las subredes salen del rango con cidrsubnet(var.cidr, 8, 1), 2 y 3. Tras añadir o cambiar un module, hay que repetir terraform init. Así se levantarán los laboratorios de los bloques siguientes: un módulo probado, un apply.
