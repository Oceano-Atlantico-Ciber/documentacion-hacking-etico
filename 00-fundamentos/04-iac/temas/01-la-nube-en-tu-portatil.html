La nube en tu portátil

Una nube como AWS es un centro de datos que se maneja entero con peticiones HTTP: crear un disco, un usuario o un servidor es mandar una petición firmada a una API. Floci es un programa que responde a esas mismas peticiones dentro de un contenedor. Con él trabajas como en AWS, sin cuenta, sin tarjeta y sin que nada salga de tu equipo.

Antes: Docker 4 · Compose y seguridadEjercicios: E1 y E2

Palabras de este tema

Cuenta
El contenedor de todo lo que creas en AWS. Tiene un número de doce cifras y un usuario raíz que lo puede todo.
Región
Un grupo de centros de datos en una zona del mundo, como eu-west-1 (Irlanda). Casi todo lo que creas vive en una región.
Servicio
Cada producto de AWS, con su propia API: S3 guarda ficheros, IAM gestiona identidades y permisos, EC2 da servidores, RDS bases de datos.
Clave de acceso
La pareja AccessKeyId y SecretAccessKey con la que un programa firma sus peticiones. Quien la tiene actúa como su dueño.
ARN
El nombre completo de un recurso: arn:aws:s3:::copias-1a2b3c4d, arn:aws:iam::000000000000:user/becario.
Endpoint
La dirección a la que se mandan las peticiones. En AWS es https://s3.eu-west-1.amazonaws.com; con Floci, http://localhost:4566.

Cuatro servicios para empezar

AWS tiene más de doscientos servicios. En esta unidad usas cuatro, los que aparecen en casi cualquier auditoría de una cuenta:

ServicioQué guardaLo que mira un auditor
S3Ficheros (objetos) dentro de cubos (buckets) con un nombre único.Cubos públicos, sin cifrar, con copias o datos personales.
IAMUsuarios, grupos, roles y las políticas que dicen qué puede hacer cada uno.Permisos de más, claves viejas o filtradas, quién puede darse permisos.
EC2Servidores virtuales y las redes (VPC) y grupos de seguridad que los rodean.Puertos abiertos a todo internet, secretos en el arranque.
RDSBases de datos gestionadas: PostgreSQL, MySQL…Bases accesibles desde fuera, sin cifrar, sin copias.

Floci: una cuenta AWS en un contenedor

Floci habla el mismo protocolo que AWS, así que la CLI de AWS y Terraform funcionan con él sin cambiar nada, salvo el endpoint. En el curso lo usamos con tres ajustes, que ya trae el docker-compose.yml que te deja preparar.py:

  • Versión fija, floci/floci:2.4.0. Con latest, una versión nueva podría cambiar el comportamiento a mitad de curso.
  • Permisos de IAM aplicados (FLOCI_SERVICES_IAM_ENFORCEMENT_ENABLED). Por defecto Floci deja hacer todo a cualquiera; así, cada usuario solo puede lo que dice su política, como en AWS.
  • Servidores y bases de datos simulados (FLOCI_SERVICES_EC2_MOCK y FLOCI_SERVICES_RDS_MOCK). Existen en la API con toda su configuración, pero no arrancan contenedores. Para aprender a describirlos con Terraform y revisarlos es lo que importa.

La clave test / test es la del usuario raíz de la cuenta emulada: puede con todo. Las claves que crees para otros usuarios solo podrán lo que les dé su política.

Floci emula la API, no la nube entera. Algunos detalles difieren de AWS y se dicen donde importan. Lo que aprendes (los recursos, sus opciones y sus fallos) es el de AWS.

Prepara tu equipo

Docker Desktop ya lo tienes de Docker 1. Abre PowerShell e instala la CLI de AWS y Terraform:

winget install -e --id Amazon.AWSCLI
winget install -e --id Hashicorp.Terraform

Cierra Git Bash y vuelve a abrirlo para que encuentre los programas nuevos, y comprueba:

aws --version
terraform version

Ahora dile a la CLI de AWS dónde está tu nube. Estas cuatro órdenes escriben la configuración por defecto en ~/.aws/, una sola vez:

aws configure set aws_access_key_id test
aws configure set aws_secret_access_key test
aws configure set region eu-west-1
aws configure set endpoint_url http://localhost:4566

Con esta configuración, cada orden aws va a Floci y nunca a AWS de verdad. Si algún día usas una cuenta real, créale otro perfil con --profile.

Levantar la nube

Toda la unidad usa una sola Floci, la de fundamentos/iac/ de tu repositorio de entregas. preparar.py deja allí el docker-compose.yml la primera vez que lo lanzas:

cd fundamentos/iac
docker compose up -d
aws sts get-caller-identity

La última orden pregunta «¿quién soy?». Si responde un JSON con la cuenta (Account) y tu ARN, tu nube funciona. Lo que crees se guarda en un volumen de Docker y sigue ahí tras docker compose down; con docker compose down -v empiezas de cero.

La CLI de AWS

Todas las órdenes tienen la misma forma: aws <servicio> <acción> --opciones. Las acciones son las de la API: create-user llama a CreateUser. Para S3 hay además unas órdenes cortas, aws s3, que se parecen a las de la shell:

aws s3 mb s3://pruebas-1a2b3c4d                    # crear un bucket
aws s3 cp informe.txt s3://pruebas-1a2b3c4d/        # subir un fichero
aws s3 ls s3://pruebas-1a2b3c4d                     # listar
aws iam create-user --user-name ana                 # crear un usuario
aws iam list-users                                  # listar los usuarios
aws iam list-user-policies --user-name ana          # sus políticas en línea

Las respuestas son JSON. Para quedarte con un dato, --query recorre la respuesta: aws iam list-users --query "Users[].UserName". Cuando una orden falla, la última línea dice por qué: AccessDenied es un permiso que falta, NoSuchEntity algo que no existe.

Políticas de IAM

Un usuario recién creado no puede hacer nada. Lo que puede hacer lo dicen sus políticas: documentos JSON con una lista de sentencias. Cada sentencia dice si permite o deniega (Effect), qué acciones (Action) y sobre qué recursos (Resource):

{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": "s3:ListBucket", "Resource": "arn:aws:s3:::informes-1a2b3c4d" },
    { "Effect": "Allow", "Action": "s3:GetObject",  "Resource": "arn:aws:s3:::informes-1a2b3c4d/*" }
  ]
}

Este usuario puede listar un bucket y leer sus ficheros, y nada más: ni borrarlos, ni ver otros buckets, ni tocar IAM. Fíjate en los dos ARN: el bucket para listarlo, y bucket/* para los objetos de dentro.

Una política se puede guardar en línea, dentro del usuario (put-user-policy), o como política gestionada aparte que se adjunta a varios (attach-user-policy). La regla que guía todo esto es la del menor privilegio: cada identidad, solo lo que necesita para su trabajo.

aws iam put-user-policy --user-name ana --policy-name lectura-informes --policy-document file://politica.json
aws iam create-access-key --user-name ana

create-access-key enseña el secreto una sola vez. En una cuenta real es una credencial: no la pegues en un chat ni la subas a un repositorio. En IaC 4 verás qué pasa cuando ocurre.

Lo que haces a mano no queda en ningún sitio

Has creado un bucket, un usuario y su política con cinco órdenes. ¿Cómo sabrá un compañero qué hay en la cuenta y por qué? ¿Cómo lo repites en otra cuenta, o después de un down -v? Guardar las órdenes en un fichero ayuda, pero no dice qué existe ahora: si alguien cambia algo a mano, el fichero ya no cuenta la verdad.
