La nube en tu portátil

Una nube como AWS es un centro de datos que se maneja entero con peticiones HTTP: crear un disco, un usuario o un servidor es mandar una petición firmada a una API. Floci es un programa que responde a esas mismas peticiones dentro de un contenedor. Con él trabajas como en AWS, sin cuenta, sin tarjeta y sin que nada salga de tu equipo.

Antes: Docker 4 · Compose y seguridadEjercicios: E1 y E2

Palabras de este tema

Cuenta
Agrupa todo lo que creas en AWS. Tiene un número de doce cifras y un usuario raíz, el dueño de la cuenta, que lo puede todo.
Región
Un grupo de centros de datos en una zona del mundo, como eu-west-1 (Irlanda). Casi todo lo que creas vive en una región.
Servicio
Cada producto de AWS, con su propia API: S3 guarda ficheros, IAM gestiona identidades y permisos, EC2 da servidores, RDS bases de datos.
Clave de acceso
La pareja AccessKeyId y SecretAccessKey con la que un programa firma sus peticiones: el usuario y la contraseña de los programas. Quien la tiene actúa como su dueño.
ARN
Amazon Resource Name: el nombre completo y único de un recurso en AWS. Dice el servicio, la cuenta y el recurso: arn:aws:s3:::copias-1a2b3c4d es un bucket; arn:aws:iam::000000000000:user/becario, un usuario.
Punto de acceso (endpoint)
La dirección a la que se mandan las peticiones. En AWS es, por ejemplo, https://s3.eu-west-1.amazonaws.com; con Floci, http://localhost:4566.

Cuatro servicios para empezar

AWS tiene más de doscientos servicios. En esta unidad usas cuatro, los que aparecen en casi cualquier auditoría de una cuenta:

ServicioQué guardaLo que mira un auditor
S3Ficheros (objetos) dentro de buckets: contenedores de ficheros con un nombre único en todo AWS.Buckets públicos, sin cifrar, con copias o datos personales.
IAMUsuarios, grupos, roles y las políticas que dicen qué puede hacer cada uno.Permisos de más, claves viejas o filtradas, quién puede darse permisos.
EC2Servidores virtuales y las redes (VPC) y grupos de seguridad que los rodean.Puertos abiertos a todo internet, secretos en el arranque.
RDSBases de datos gestionadas: PostgreSQL, MySQL…Bases accesibles desde fuera, sin cifrar, sin copias.

Floci: una cuenta AWS en un contenedor

Floci habla el mismo protocolo que AWS, así que la CLI de AWS y Terraform funcionan con él sin cambiar nada, salvo el punto de acceso:

En el curso se usa con tres ajustes, que ya trae el docker-compose.yml que te deja preparar.py:

  • Versión fija, floci/floci:2.4.0. Con latest, una versión nueva podría cambiar el comportamiento a mitad de curso.
  • Permisos de IAM aplicados. Por defecto, Floci deja hacer todo a cualquiera. Con este ajuste, cada usuario solo puede lo que dice su política, como en AWS.
  • Servidores y bases de datos simulados. Existen en la API con toda su configuración, pero no arrancan ningún sistema de verdad. Para aprender a describirlos con Terraform y revisarlos, basta con eso.

Floci trae una clave ya hecha, test / test: es la del usuario raíz de la cuenta simulada y puede con todo. En esta unidad se llama la clave de administrador. Las claves que crees para otros usuarios solo podrán lo que les dé su política.

Floci emula la API, no la nube entera. Algunos detalles difieren de AWS y se dicen donde importan. Lo que aprendes (los recursos, sus opciones y sus fallos) es el de AWS.

Prepara tu equipo

Trabajas en la terminal de VS Code (Terminal → New Terminal): en Windows es PowerShell; en macOS y Linux, la Terminal. Docker Desktop ya lo tienes de Docker 1. Instala la CLI de AWS y Terraform:

Windows · PowerShell

winget install -e --id Amazon.AWSCLI
winget install -e --id Hashicorp.Terraform

macOS / Linux · Terminal

brew install awscli terraform

En Linux sin Homebrew, sigue las guías oficiales: CLI de AWS y Terraform.

En Windows, winget cambia el PATH, pero la terminal abierta no se entera: cierra VS Code entero y vuelve a abrirlo (abrir otra pestaña de terminal no basta). Después comprueba que los dos programas responden:

aws --version
terraform version
aws-cli/2.x.x Python/3.x.x Windows/11 exe/AMD64
Terraform v1.x.x
on windows_amd64

Tus números serán otros, y en macOS o Linux saldrá tu sistema. Si dice que no reconoce aws o terraform, no has reabierto VS Code.

Ahora dile a la CLI de AWS dónde está tu nube. Estas cuatro órdenes escriben la configuración por defecto en la carpeta .aws de tu usuario. Se lanzan una sola vez, desde cualquier carpeta, y son iguales en los dos sistemas:

aws configure set aws_access_key_id test
aws configure set aws_secret_access_key test
aws configure set region eu-west-1
aws configure set endpoint_url http://localhost:4566

No escriben nada en pantalla. Las dos primeras guardan la clave de administrador; la tercera, la región; la cuarta, endpoint_url, manda las peticiones a tu equipo en vez de a Amazon.

Con esta configuración, cada orden aws va a Floci y nunca a AWS de verdad. Si algún día usas una cuenta real, guarda su configuración en otro perfil (una configuración con nombre propio) con la opción --profile.

Levanta la nube

Toda la unidad usa una sola Floci, la de fundamentos/iac/ de tu repositorio de entregas. preparar.py deja allí el docker-compose.yml la primera vez que lo lanzas (en el E1). Con Docker Desktop abierto, desde la carpeta de tu repositorio:

cd fundamentos/iac
docker compose up -d
aws sts get-caller-identity

La última orden pregunta «¿quién soy?». Si responde un JSON parecido a este (con la cuenta, Account, y tu ARN), tu nube funciona:

{
    "UserId": "…",
    "Account": "000000000000",
    "Arn": "arn:aws:iam::000000000000:root"
}

Si sale Could not connect to the endpoint URL, Floci no está en marcha: mira docker compose ps o espera unos segundos tras el up -d. Lo que crees se guarda en un volumen de Docker y sigue ahí tras docker compose down o un reinicio; con docker compose down -v lo borras todo y empiezas de cero.

La CLI de AWS

Todas las órdenes tienen la misma forma: aws <servicio> <acción> --opciones. Las acciones son las de la API: create-user llama a CreateUser. Para S3 hay además unas órdenes cortas, aws s3, que se parecen a las de la terminal:

aws s3 mb s3://pruebas-1a2b3c4d                    # crear un bucket
aws s3 cp informe.txt s3://pruebas-1a2b3c4d/        # subir un fichero
aws s3 ls s3://pruebas-1a2b3c4d                     # listar
aws iam create-user --user-name ana                 # crear un usuario
aws iam list-users                                  # listar los usuarios
aws iam list-user-policies --user-name ana          # sus políticas en línea

Lo que va detrás de # es un comentario, aquí y en los dos sistemas. Para recorrer una cuenta bastan tres verbos: list-… (qué hay), get-… (los detalles de uno) y, en EC2 y RDS, describe-… (las dos cosas a la vez, por ejemplo aws ec2 describe-instances). Las respuestas son JSON. Para quedarte con un dato, --query recorre la respuesta: aws iam list-users --query "Users[].UserName". Cuando una orden falla, la última línea dice por qué: AccessDenied es un permiso que falta, NoSuchEntity algo que no existe. Si una respuesta larga se queda parada en -- More --, pulsa espacio para seguir o q para salir.

Escribe cada orden en una sola línea, aunque sea larga. En PowerShell, la \ del final de línea que verás en otras guías no sirve para continuar una orden.

Políticas de IAM

Un usuario recién creado no puede hacer nada. Lo que puede hacer lo dicen sus políticas: documentos JSON con una lista de sentencias. Cada sentencia dice si permite o deniega (Effect), qué acciones (Action) y sobre qué recursos (Resource):

{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": "s3:ListBucket", "Resource": "arn:aws:s3:::informes-1a2b3c4d" },
    { "Effect": "Allow", "Action": "s3:GetObject",  "Resource": "arn:aws:s3:::informes-1a2b3c4d/*" }
  ]
}

"Version": "2012-10-17" es la versión del lenguaje de las políticas, no una fecha tuya: se escribe siempre así. Este usuario puede listar un bucket y leer sus ficheros, y nada más: ni borrarlos, ni ver otros buckets, ni tocar IAM. Fíjate en los dos ARN: el del bucket, para listarlo, y bucket/*, para los objetos de dentro.

Una política se puede guardar de dos formas. En línea (inline): va dentro del propio usuario y es solo suya (put-user-policy). Gestionada: es una política aparte, con su propio ARN, que se adjunta a varios usuarios (attach-user-policy). La regla que guía todo esto es la del menor privilegio: cada identidad, solo lo que necesita para su trabajo.

El JSON de la política va en un fichero, por ejemplo politica.json, que creas con VS Code en la carpeta donde lanzas la orden. file:// le dice a la CLI que lea el fichero:

aws iam put-user-policy --user-name ana --policy-name lectura-informes --policy-document file://politica.json
aws iam create-access-key --user-name ana

No escribas el JSON dentro de la propia orden: en PowerShell las comillas de dentro se pierden por el camino y la CLI recibe un JSON roto. Con un fichero, la misma orden vale en Windows, macOS y Linux.

create-access-key enseña el secreto una sola vez. En una cuenta real es una credencial: no la pegues en un chat ni la subas a un repositorio. En IaC 4 verás qué pasa cuando ocurre.

Lo que haces a mano no queda en ningún sitio

En el E1 crearás un bucket, un usuario y su política con cuatro órdenes. ¿Cómo sabrá un compañero qué hay en la cuenta y por qué? ¿Cómo lo repites en otra cuenta, o después de un down -v? Guardar las órdenes en un fichero ayuda, pero no dice qué existe ahora: si alguien cambia algo a mano, el fichero ya no cuenta la verdad.
