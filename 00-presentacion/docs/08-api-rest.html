Qué es una API REST

Una API es la puerta por la que un programa habla con un servidor. En una API REST, cada cosa tiene una dirección (URL) y el método HTTP dice qué quieres hacer con ella.

Una petición y su respuesta

Petición · lo que envías
POST /api/players HTTP/1.1
Host: localhost:8080
Content-Type: application/json
Authorization: Bearer eyJhbGci…

{"name": "ana"}
Respuesta · lo que devuelve
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/players/ana

{"name": "ana", "score": 0}
MétodoQué quieres hacer: leer, crear, cambiar, borrar.
Ruta (URL)Sobre qué recurso: /api/players/ana.
CabecerasDatos sobre la petición: formato, quién eres.
CuerpoLos datos, casi siempre en JSON.

Los métodos

Pulsa un método para ver la petición y la respuesta típicas. Los ejemplos usan una API inventada de jugadores en http://localhost:8080, la dirección del juego si lo levantas en tu equipo. Si usas otra, cámbiala; las rutas reales las sacas tú de F12.

GET

Leer un recurso o una lista. No cambia nada en el servidor.

Seguro Idempotente Lleva cuerpo

Códigos de estado

  
El primer dígito ya te dice mucho: 2 bien, 4 te has equivocado tú, 5 ha fallado el servidor.

  

    
CódigoNombreCuándo lo verás

    
      
200OKLa petición ha funcionado.

      
201CreatedSe ha creado un recurso nuevo (típico de POST).

      
204No ContentHecho, sin nada que devolver (típico de DELETE).

      
400Bad RequestFaltan datos o están mal escritos. Lee el mensaje de error.

      
401UnauthorizedNo has dicho quién eres, o la credencial no vale.

      
403ForbiddenSé quién eres, pero no tienes permiso.

      
404Not FoundEsa ruta o ese recurso no existe.

      
405Method Not AllowedLa ruta existe, pero no con ese método.

      
429Too Many RequestsVas demasiado rápido: hay límite de peticiones.

      
500Internal Server ErrorEl servidor ha fallado al procesarla.

      
502Bad GatewayUn intermediario (un túnel, un proxy) no llega al servidor.

    
  






  
Cabeceras que más vas a ver

  

    
CabeceraPara qué sirve

    
      
Content-TypeFormato del cuerpo. En APIs: application/json.

      
AuthorizationQuién eres: un token o una clave. Sin ella, el servidor no sabe quién pide.

      
CookieOtra forma de identificarte, la que usan las webs con sesión.

      
X-…Cabeceras inventadas por cada aplicación. Las escribe el cliente, así que puede poner lo que quiera.

    
  






  
Tres reglas para mirar una API con ojos de seguridad

  

    
El cliente es tuyo
Todo lo que manda el navegador lo puede cambiar quien lo usa. El servidor tiene que validar cada dato.

    
Cada petición va sola
REST no recuerda nada entre peticiones. Si una acción necesita saber quién eres, la petición debe probarlo.

    
Cada método, su papel
Un GET no debería cambiar nada. Si lo hace, basta con abrir un enlace para provocar el cambio.

  






  
Dónde verlas

  

    
HerramientaCómo

    
      
NavegadorF12 → Network/Red → filtro Fetch/XHR. Cada fila es una petición: mira Headers, Payload y Response.

      
curl-X método · -H cabecera · --data cuerpo · -i ver código y cabeceras de la respuesta.

      
De F12 a curlBotón derecho sobre una petición en Network → Copy → Copy as cURL. Pégala en la terminal y cambia lo que quieras probar.
