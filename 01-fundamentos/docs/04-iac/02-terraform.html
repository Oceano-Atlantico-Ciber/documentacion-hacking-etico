Terraform

Infraestructura como código: en vez de crear los recursos a mano, escribes en ficheros cómo tiene que quedar la cuenta, y una herramienta hace las llamadas a la API que faltan para llegar ahí. El código se revisa, se versiona con git y se repite igual cuantas veces quieras. Durante el curso, los laboratorios se levantarán así.

Antes: IaC 1 · La nube en tu portátilEjercicios: E3 y E4

Palabras de este tema

Declarativo
Describes el resultado («un bucket llamado así»), no los pasos. Terraform calcula los pasos.
Proveedor
El complemento que sabe hablar con una API concreta: hashicorp/aws para AWS (y para Floci).
Recurso
Un objeto de la cuenta descrito en el código: resource "aws_s3_bucket" "notas" { … }.
Estado
El fichero terraform.tfstate, donde Terraform apunta qué recurso real corresponde a cada bloque del código.
Plan
La lista de cambios que haría Terraform para que la cuenta quede como el código: crear, cambiar, destruir.
Deriva
La diferencia entre el código y la cuenta cuando alguien cambia algo a mano.

Un fichero de Terraform

Terraform lee todos los ficheros .tf de la carpeta en la que lo lanzas, como si fueran uno. El lenguaje se llama HCL y tiene bloques con un tipo, unas etiquetas y unos argumentos. En los ejercicios, proveedor.tf ya viene hecho: dice que se usa el proveedor de AWS y que sus peticiones van a Floci. Tú escribes los recursos:

resource "aws_s3_bucket" "informes" {          # tipo de recurso y nombre en el código
  bucket = "informes-1a2b3c4d"                 # nombre en la cuenta
}

resource "aws_iam_user" "ana" {
  name = "ana-1a2b3c4d"
}

resource "aws_iam_user_policy" "lectura" {
  name = "lectura-informes"
  user = aws_iam_user.ana.name                 # referencia a otro recurso
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      { Effect = "Allow", Action = "s3:ListBucket", Resource = aws_s3_bucket.informes.arn },
      { Effect = "Allow", Action = "s3:GetObject",  Resource = "${aws_s3_bucket.informes.arn}/*" },
    ]
  })
}

Tres ideas en este ejemplo:

  • Cada recurso tiene dos nombres: el del código (informes), para referirte a él, y el de la cuenta (informes-1a2b3c4d).
  • aws_iam_user.ana.name y aws_s3_bucket.informes.arn son referencias. Además de evitar repetir nombres, le dicen a Terraform el orden: la política se crea después del usuario y del bucket.
  • jsonencode escribe la política en HCL y la convierte a JSON. Es la misma política de IaC 1.

Qué argumentos tiene cada recurso lo dice la documentación del proveedor, en el registro de Terraform: busca «aws_iam_user_policy terraform» y abre la página de registry.terraform.io.

El ciclo: init, plan, apply

Desde la carpeta con los .tf:

OrdenQué hace
terraform initDescarga el proveedor a .terraform/. Una vez por carpeta, o al cambiar de proveedor.
terraform fmtOrdena el formato de tus ficheros. Pásalo siempre antes de un commit.
terraform validateComprueba que el código tiene sentido sin tocar la cuenta.
terraform planCompara código, estado y cuenta, y enseña lo que cambiaría: + crear, ~ cambiar, - destruir.
terraform applyEnseña el plan, pide confirmación (yes) y hace las llamadas.
terraform outputMuestra las salidas que declara el código.
terraform destroyBorra todo lo que el estado dice que gestiona este código.

La línea que más importa del plan es la última, por ejemplo Plan: 3 to add, 0 to change, 0 to destroy. Léela siempre antes de escribir yes. Después de un apply, un segundo plan tiene que decir No changes: el código y la cuenta coinciden. Si no, algo en tu código no describe bien lo que existe.

El estado, y por qué no se sube

Terraform guarda en terraform.tfstate qué recurso real es cada bloque, con todos sus atributos. Ahí aparecen también los secretos: contraseñas de bases de datos, claves de acceso que cree tu código. Por eso el .gitignore de la unidad deja fuera el estado, .terraform/ y el fichero de bloqueo. En un equipo, el estado vive en un almacén compartido y cifrado; en el curso, en tu carpeta.

Si borras el estado, Terraform «olvida» lo que creó: el siguiente plan querrá crearlo todo otra vez y chocará con lo que ya existe. Para recuperar recursos que existen sin estado está import.

Adoptar lo que ya existe: import

Casi nunca se empieza de cero: la cuenta ya tiene cosas creadas a mano. Un bloque import le dice a Terraform que un recurso del código corresponde a uno que ya existe, en vez de crearlo:

import {
  to = aws_iam_user.ana          # el bloque del código
  id = "ana-1a2b3c4d"            # cómo encontrarlo en la cuenta
}

Qué es el id lo dice la página de cada recurso, en su sección «Import»: para un bucket, su nombre; para un usuario, su nombre; para una política en línea, usuario:política. Con el bloque en su sitio, el plan dice 1 to import. Si además dice to change, tu código no describe el recurso tal como está: ajústalo hasta que el plan solo importe, y entonces aplica. Después, los bloques import pueden quedarse o borrarse; ya no hacen nada.

Variables y salidas

Un nombre que se repite en diez sitios es un error esperando a pasar. Las variables son los parámetros del código y las salidas lo que devuelve:

# variables.tf
variable "huella" {
  description = "La parte de los nombres que distingue mis recursos"
  type        = string
  default     = "1a2b3c4d"
}

# main.tf
resource "aws_s3_bucket" "informes" {
  bucket = "informes-${var.huella}"
}

# outputs.tf
output "bucket" {
  value = aws_s3_bucket.informes.bucket
}

Una variable sin default se pide al lanzar el plan, o se pasa con -var huella=… o un fichero .tfvars. Las que llevan secretos se marcan sensitive = true y Terraform no las enseña en pantalla (aunque sí quedan en el estado).

Deriva: cuando alguien toca a mano

Un compañero arregla algo con la CLI, sin pasar por el código. La cuenta ya no es lo que dice el código, y nadie lo ve hasta el siguiente plan, que lo detecta porque pregunta a la API cómo está cada recurso:

  # aws_iam_user_policy.lectura will be created
  + resource "aws_iam_user_policy" "lectura" {
…
Plan: 1 to add, 0 to change, 0 to destroy.

El código es la fuente de verdad: un apply deja la cuenta otra vez como dice el código, y el cambio a mano se pierde. Si el cambio era bueno, se hace en el código, con su commit y su revisión. Pasar el plan cada día y avisar si no sale vacío es una forma sencilla de vigilar una cuenta.
