Cliente, servidor y HTTP

Casi todo lo que auditaremos habla con un servidor a través de una API. Antes de buscarle fallos hay que saber leer esa conversación: quién pregunta, qué viaja por la red y en qué formato.

Práctica de la unidad: Hackea el ranking

Qué es una API

Una API (Application Programming Interface) es la puerta que un programa ofrece a otros programas. Piensa en el mostrador de una cafetería: no entras a la cocina, pides en el mostrador con unas palabras acordadas y te devuelven lo que has pedido. Quien pide es el cliente; quien atiende, el servidor.

Un mismo servidor suele atender a dos tipos de cliente. A una persona con su navegador le devuelve páginas en HTML, pensadas para leerse. A un programa le devuelve datos en JSON, pensados para procesarse. La página que ves en el navegador suele ser las dos cosas: llega en HTML y después su JavaScript pide datos a la API.

El viaje de una petición

Cada vez que un cliente necesita algo del servidor hace una petición y espera una respuesta. Siempre es el cliente quien empieza: el servidor solo contesta. Recorre el viaje paso a paso.

HTTP: la conversación es texto

Cliente y servidor hablan HTTP. Una petición y una respuesta HTTP son texto con un orden fijo, y eso es lo que las hace tan fáciles de leer y de modificar. Esta es la petición del viaje anterior y su respuesta:

GET /api/players/1 HTTP/1.1
Host: api.ranking.example
Accept: application/json
HTTP/1.1 200 OK
Content-Type: application/json

{"id": 1, "name": "ana", "score": 42}
  • La primera línea de la petición dice qué quieres (GET, leer) y sobre qué (/api/players/1). La de la respuesta, cómo ha ido: 200 OK.
  • Después van las cabeceras, una por línea con la forma Nombre: valor: datos sobre el mensaje, como a qué máquina va o en qué formato está el cuerpo.
  • Tras una línea en blanco, el cuerpo: los datos. Una petición de lectura no lleva cuerpo.

Cada pieza (método, códigos y cabeceras) se desmonta en el tema siguiente. Con HTTPS el texto es el mismo, pero viaja cifrado: nadie en la red puede leerlo ni cambiarlo por el camino. El cifrado protege el viaje; lo que se envía lo sigue decidiendo el cliente.

Las partes de una URL

La URL es la dirección completa de lo que pides. Cambia la de abajo, o elige un ejemplo, y mira cómo se descompone.

REST: cada cosa tiene su dirección

REST es una forma de organizar una API: cada cosa que maneja el servidor es un recurso con su propia ruta, y las rutas se escriben como nombres, no como acciones. Lo que quieres hacer con el recurso lo dice el método, como verás en el tema siguiente.

Así síAsí noPor qué
/api/players/1/api/getPlayer?id=1La ruta nombra el recurso; leer lo dice el método.
/api/players/api/player-listLa colección y sus elementos comparten raíz.

Muchas APIs no siguen estas reglas al pie de la letra. Para auditar no hace falta que la API sea bonita, sino entender qué ruta toca qué datos.

JSON: el formato de los datos

Las APIs se intercambian los datos en JSON, un texto con seis tipos de valor:

TipoEjemploPara qué
Objeto{"name": "ana", "score": 42}Pares clave y valor. Las claves, siempre entre comillas dobles.
Lista[1, 2, 3]Valores en orden.
Texto"ana"Siempre con comillas dobles.
Número42, 3.5Sin comillas.
Booleanotrue, falseSí o no.
NulonullSin valor.

Un error de una sola coma hace que el servidor rechace la petición entera. Escribe o pega JSON en la caja y comprueba si es válido; los botones cargan los tres errores más habituales.

Comprobación

  • Sabes explicar quién empieza siempre la conversación y qué devuelve el servidor a una persona y a un programa
  • Distingues en un mensaje HTTP la primera línea, las cabeceras y el cuerpo
  • Sabes qué parte de una URL no llega nunca al servidor
  • Lees una ruta REST y dices si apunta a una colección o a un elemento
  • Encuentras el fallo de un JSON que el servidor rechaza
