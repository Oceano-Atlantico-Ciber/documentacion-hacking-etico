Construir imágenes

Una imagen se construye con una receta, el Dockerfile, y cada paso de la receta queda guardado como una capa. Entender las capas explica por qué una construcción tarda un segundo o cinco minutos, y por qué borrar un secreto no lo borra.

Ejercicios: E2, E3 y E4

El Dockerfile

Un Dockerfile es un fichero de texto con una instrucción por línea. Docker las ejecuta en orden, de arriba abajo, partiendo de una imagen que ya existe.

InstrucciónQué hace
FROM python:3.12-alpineImagen de partida. Siempre la primera.
WORKDIR /appCarpeta de trabajo dentro de la imagen; las demás instrucciones se ejecutan ahí.
COPY sondeo.py .Copia ficheros de tu carpeta a la imagen.
RUN pip install requestsEjecuta una orden durante la construcción y guarda lo que cambie.
ENV MODO=seguroVariable de entorno para el contenedor.
USER nobodyUsuario con el que se ejecuta el programa. Sin ella, root (Docker 4).
ENTRYPOINT ["python", "sondeo.py"]El programa que arranca el contenedor.
CMD ["--ayuda"]Argumentos por defecto, si al lanzarlo no das otros.
docker build -t sondeo:1.0 .     # construye con el Dockerfile de esta carpeta y lo llama sondeo:1.0
docker image ls sondeo           # ya está entre tus imágenes
docker run --rm sondeo:1.0 …     # y se usa como cualquier otra

El punto final de docker build no es decorativo: es la carpeta que se envía al motor, el contexto. Lo verás más abajo.

ENTRYPOINT y CMD

Cuando lanzas un contenedor, Docker junta dos piezas para formar la orden que ejecuta: el ENTRYPOINT, fijo, y los argumentos. Si escribes argumentos después del nombre de la imagen, sustituyen al CMD.

Cada instrucción, una capa

Las instrucciones que cambian ficheros (COPY, RUN) guardan el resultado como una capa: solo las diferencias respecto a la anterior. Una imagen es la pila de capas de su imagen de partida más las suyas. Las que solo configuran (ENV, ENTRYPOINT, CMD) no añaden ficheros.

docker history sondeo:1.0        # las capas de una imagen, la más reciente arriba, con su tamaño
docker image inspect sondeo:1.0  # su configuración: ENTRYPOINT, CMD, ENV, USER…

La caché

Al reconstruir, Docker reutiliza cada capa cuya instrucción y ficheros no han cambiado. En cuanto una capa cambia, todas las de encima se rehacen. Por eso el orden importa: lo que cambia poco va abajo y lo que cambias a menudo, arriba.

docker build --progress=plain -t app:1.0 .   # muestra cada paso; los reutilizados dicen CACHED

El contexto y .dockerignore

docker build . envía al motor toda la carpeta, y COPY . . mete en la imagen todo lo que llegó. Si en la carpeta hay un .env o tus notas, acaban dentro de la imagen y viajan con ella. .dockerignore es a Docker lo que .gitignore a git: lo que aparece ahí no se envía.

# .dockerignore: un patrón por línea, como .gitignore
.env
notas/
.git/

Un secreto en una capa

Las capas solo se añaden. Si una capa copia una clave y otra posterior la borra, la imagen final no la muestra, pero la capa que la copió sigue dentro y viaja con la imagen. Es el mismo problema que el commit que filtró una clave en Git 4.

Para usar un secreto durante la construcción sin guardarlo, BuildKit (el constructor de Docker Desktop) lo monta solo mientras dura un RUN, en /run/secrets/, y no lo escribe en ninguna capa:

# en el Dockerfile
RUN --mount=type=secret,id=api python informe.py --comprobar /run/secrets/api

# al construir: el secreto sale de un fichero tuyo, que no está en el contexto
docker build --secret id=api,src=api.key -t informe:2.0 .

Y para buscar secretos en una imagen ajena, como haría un auditor:

docker history --no-trunc imagen:versión        # qué hizo cada capa
docker save imagen:versión -o imagen.tar         # todas las capas en un fichero
mkdir capas && tar -xf imagen.tar -C capas       # cada capa es un .tar en capas/blobs/sha256/
for capa in capas/blobs/sha256/*; do tar -tf "$capa" 2>/dev/null | grep -q api.key && echo "$capa"; done

Si algo falla

MensajeCausaSolución

COPY failed: … not foundEl fichero no está en el contexto, o .dockerignore lo excluye.Revisa la ruta, relativa a la carpeta del contexto, y tu .dockerignore.

Regla de la IA

Si pides a una IA que te escriba un Dockerfile, revisa tú el orden de las capas y qué copia: los ejemplos que circulan usan COPY . . y latest casi siempre.

Comprobación

  • Sabes escribir un Dockerfile con FROM, WORKDIR, COPY y ENTRYPOINT y construirlo con etiqueta
  • Sabes qué parte de docker run imagen a b pone el ENTRYPOINT y cuál sustituye al CMD
  • Sabes ordenar las capas para aprovechar la caché
  • Sabes por qué un secreto borrado en una capa posterior sigue en la imagen, y cómo evitarlo
