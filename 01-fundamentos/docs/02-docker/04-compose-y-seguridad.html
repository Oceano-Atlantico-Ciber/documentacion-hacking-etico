Del fichero al laboratorio

En vez de una orden docker run por contenedor, con sus -v, -p y --network, se escribe una vez qué servicios, redes y volúmenes hay. docker compose up -d crea lo que falte y arranca todo.

up, run y exec

Las tres órdenes ejecutan algo en un servicio, pero no en el mismo contenedor. Confundirlas es el error más común con los laboratorios.

OrdenQué hace
docker compose up -dCrea y arranca los servicios sin perfil. Si cambias el fichero y repites, recrea solo lo que cambió.
docker compose ps / logs -f suricataEstado de los servicios / lo que escribe uno.
docker compose run --rm curl -i http://web/Contenedor de un solo uso del servicio curl; lo de detrás son sus argumentos.
docker compose restart suricataReinicia un servicio, por ejemplo tras cambiar sus reglas.
docker compose up -d --force-recreate flociLo recrea aunque no haya cambiado.
docker compose down / down -vPara y borra contenedores y redes / también los volúmenes.
docker compose configEl fichero tal como lo entiende Docker, con las variables ya sustituidas. Sirve para revisar.

Perfiles

Un servicio con profiles: no se arranca con up. Así el laboratorio separa lo que debe estar siempre en marcha de las herramientas que se lanzan cuando hacen falta.

Variables y secretos

Un compose puede leer valores de fuera con ${VARIABLE}. Docker las busca en tu entorno y en un fichero .env junto al compose. Así la contraseña no se escribe en un fichero que se sube a git.

FormaSi la variable no existe
${POSTGRES_PASSWORD}Queda vacía, y Docker solo avisa.
${POSTGRES_PASSWORD:-cambiar-en-clase}Usa el valor por defecto. Es lo que hace la Mini auditoría.
${POSTGRES_PASSWORD:?falta en .env}Se niega a arrancar con ese mensaje. Lo más seguro para un secreto.
# .env: junto al compose; ya está en el .gitignore de tu repositorio
POSTGRES_PASSWORD=una-larga-y-solo-tuya

# .env.ejemplo: este sí se sube, para que otro sepa qué variables hacen falta
POSTGRES_PASSWORD=

Los compose del curso repiten las credenciales de AWS en tres servicios con un ancla de YAML: &aws pone nombre a un bloque y *aws lo reutiliza. No es de Docker, es del formato YAML.

environment: &aws          # el bloque se llama aws
  AWS_ENDPOINT_URL: http://floci:4566
…
environment: *aws          # el mismo bloque, sin copiarlo

Puertas que abre un compose

Un contenedor está aislado del equipo, pero algunas líneas del compose abren puertas hacia él. Ordenadas de menos a más poder:

Lista para revisar cualquier compose, también los que te dé una IA:

  • Versión fija en cada imagen, sin latest salvo decisión consciente.
  • Puertos en 127.0.0.1, y solo los que se usan desde fuera; las bases de datos, ninguno.
  • Sin docker.sock ni privileged; si hace falta un permiso, el cap_add concreto.
  • Carpetas en :ro salvo que el contenedor deba escribir en ellas.
  • Secretos en .env, con ${VAR:?…}, y el .env fuera de git.
  • Usuario no root en las imágenes propias (USER en el Dockerfile).

Para el Dockerfile, trivy config revisa la mayoría de estos puntos solo, igual que hiciste con Terraform:

docker run --rm -v ./:/work:ro aquasec/trivy:0.58.0 config --severity HIGH,CRITICAL /work
