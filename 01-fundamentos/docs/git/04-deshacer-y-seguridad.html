Deshacer y seguridad

Casi todo en git se puede deshacer, y casi nada se borra del todo. Eso salva trabajo y, a la vez, convierte un repositorio en una fuente de información para un atacante.

JuevesEjercicios: E7 y E8

Qué orden para qué situación

SituaciónOrden
Descartar los cambios de un fichero que no has añadido.git restore fichero
Sacar un fichero del índice sin perder tus cambios.git restore --staged fichero
Corregir el último commit, aún sin subir.git commit --amend
Mover tu rama a un commit anterior, aún sin subir.git reset <commit>
Deshacer un commit que ya está en el remoto.git revert <commit>

git reset mueve la rama hacia atrás, y los commits que quedan delante dejan de estar en ella. Su opción decide qué pasa con tus ficheros:

RamaÍndiceDirectorio de trabajo
--softSe mueveIntacto: los cambios quedan listos para commitIntacto
--mixed (por defecto)Se mueveSe vacíaIntacto: los cambios siguen en tus ficheros
--hardSe mueveSe vacíaSe pierde lo no commiteado

git revert no borra nada: crea un commit nuevo que aplica el cambio inverso. Es la única forma correcta de deshacer en una rama compartida, por la regla de oro de Git 3.

La red de seguridad: reflog

Git anota en el reflog cada posición por la que ha pasado HEAD durante meses (90 días por defecto). Un reset --hard o un rebase desafortunado se recuperan volviendo a una entrada anterior:

git reflog                       # HEAD@{0}, HEAD@{1}… con lo que hiciste
git reset --hard 'HEAD@{2}'      # volver a donde estabas dos pasos atrás

El reflog es local: no se sube a GitHub ni viene al clonar. Por eso «lo borré y ya no está» casi nunca es verdad en tu máquina.

Secretos en la historia

Borrar un .env en un commit nuevo lo quita de la versión actual, pero sigue en el commit donde entró. Cualquiera con acceso al repositorio lo encuentra en segundos:

git log -p -S 'API_KEY'          # commits que añaden o quitan ese texto
git log --all --diff-filter=D --name-only    # ficheros que se borraron alguna vez

Para sacarlo de la historia hay que reescribirla con git filter-repo, que rehace cada commit sin ese fichero. Aun así, la clave ya no es secreta: GitHub sigue sirviendo el commit antiguo por su SHA, y cualquier clon, fork o caché anterior la conserva. Lo primero, siempre, es revocar y rotar la clave. Purgar la historia viene después. Herramientas como gitleaks o trufflehog automatizan la búsqueda en auditorías, y también la hacen los atacantes.

Git como fuente de reconocimiento

Algunos servidores publican la web copiando el repositorio entero, carpeta .git incluida. Si https://objetivo/.git/HEAD responde, se pueden descargar los objetos y reconstruir todo el código fuente con su historia: credenciales antiguas, rutas internas, nombres y correos de los desarrolladores. Es reconocimiento pasivo, y como todo en el curso, solo se hace dentro de un alcance autorizado.

Defensa: no desplegar la carpeta .git, o bloquear en el servidor web cualquier ruta que empiece por /.git.

El autor de un commit se falsifica

El autor es solo lo que dice tu configuración. Nada impide esto:

git -c user.name="Otra Persona" -c user.email="su-correo@ejemplo.com" commit -m "fix: cambio inocente"

GitHub mostrará el commit con el nombre y la foto de esa persona. La defensa es firmar los commits: GitHub marca como Verified los firmados con una clave registrada en la cuenta, y con el modo vigilante marca como Unverified los que no lo están.

git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true
# y en GitHub: Settings → SSH and GPG keys → New SSH key, tipo «Signing key»

Práctica

E7 · Revert y E8 · Secreto filtrado. En E8 subes la clave a propósito y luego la purgas: al final mira en GitHub si el commit antiguo sigue accesible.

Regla de la IA

Nunca pegues a una IA en la nube un fichero con secretos reales: en ese momento la clave ha salido de tu control. Para pedir ayuda con un .env, sustituye antes los valores.

Comprobación

  • Sabes elegir entre restore, reset y revert según si el commit está publicado
  • Sabes recuperar un commit perdido con git reflog
  • Sabes por qué una clave filtrada se rota aunque se purgue de la historia
