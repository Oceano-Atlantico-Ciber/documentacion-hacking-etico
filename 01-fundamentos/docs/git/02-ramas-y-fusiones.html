Ramas y fusiones

Una rama no es una copia del proyecto, es una etiqueta que avanza. Entender eso explica las dos formas de fusionar y de dónde sale un conflicto.

Miércoles, 2.ª horaEjercicios: E3 y E4

Una rama es un puntero

Una rama es un fichero de 41 bytes con el SHA de un commit. Al hacer commit en ella, el puntero avanza al commit nuevo. HEAD indica en qué rama estás. Crear una rama no copia nada, por eso es instantáneo.

git switch -c git/prueba      # crear una rama y pasar a ella
git switch main               # volver
git branch -v                 # ramas locales y su último commit
cat .git/refs/heads/main      # el puntero, tal cual

Dos formas de fusionar

OrdenQué hace
git merge ramaFast-forward si se puede; si no, commit de merge.
git merge --ff-only ramaSolo fast-forward; si no se puede, se niega.
git merge --no-ff ramaSiempre commit de merge, para que quede constancia de que hubo una rama.

Después de fusionar, git log --oneline --graph dibuja exactamente estos esquemas.

Conflictos

En un merge de tres vías git compara cada lado con el ancestro común (B en el esquema). Si solo un lado tocó unas líneas, se queda con ese cambio. Si los dos tocaron las mismas líneas de forma distinta, no puede decidir y para: es un conflicto. Git marca el fichero así:

22 ssh
<<<<<<< HEAD
3306 mysql
=======
5432 postgresql
>>>>>>> git/e4-b

Arriba está tu lado (HEAD) y abajo el de la rama que entra. Resolver es dejar el fichero como debe quedar, sin marcadores, y decírselo a git:

  1. git status lista los ficheros en conflicto.
  2. Edita cada uno. Puede quedar un lado, el otro, los dos o algo nuevo.
  3. git add fichero marca el conflicto como resuelto.
  4. git commit (o git merge --continue) crea el commit de merge.

Si te lías, git merge --abort deja todo como estaba antes del merge.

Práctica

E3 · Fusiones y E4 · Conflicto. En E4 la regla de resolución está en el enunciado: el corrector comprueba que hubo un conflicto real y que lo resolviste según ella.

Regla de la IA

Pega a la IA el fichero con marcadores y pídele que explique qué quería cada lado. Antes de aceptar su resolución, compárala con git diff y con la regla del enunciado: la IA no conoce la regla si no se la das.

Comprobación

  • Sabes predecir si un merge será fast-forward antes de lanzarlo
  • Sabes leer los marcadores de un conflicto y salir con git merge --abort
  • E3 y E4 superados en el check Corrector git y con su etiqueta
