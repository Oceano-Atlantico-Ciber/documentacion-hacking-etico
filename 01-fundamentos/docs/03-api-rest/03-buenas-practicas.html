Buenas prácticas

Una API bien hecha se comporta como espera cualquiera que sepa HTTP, sin leer su documentación. Errores con un formato fijo, listas por páginas, caché y cambios que no se pisan: todo se resuelve con códigos y cabeceras de HTTP, igual en Go, en Python y en Node.

Palabras de este tema

Validar
Comprobar lo que llega antes de usarlo: que es JSON, que tiene los campos que tocan y solo esos, con su tipo y su tamaño.
Problem Details
El formato estándar de los errores de una API (RFC 9457): un JSON con type, title, status y detail.
Paginar
Devolver una lista larga por trozos, con una forma de pedir el siguiente.
Cursor
La marca de dónde se quedó una página. El cliente la devuelve para pedir la siguiente.
ETag
Una etiqueta que identifica la versión actual de un recurso. Si el recurso cambia, cambia.
Petición condicional
Una petición que solo se cumple si el recurso sigue en cierta versión: If-None-Match e If-Match.

Errores que ayudan

Un error tiene dos lectores. El programa cliente necesita un código y un formato fijo para decidir qué hacer; la persona que lo depura necesita una frase que diga qué falló. La RFC 9457 define un formato para los dos, con su propio tipo, application/problem+json:

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "about:blank",
  "title": "Datos no válidos",
  "status": 422,
  "detail": "prioridad: una de baja, media, alta, critica"
}
CódigoCuándoEjemplo
400La petición no se puede leerJSON con una comilla de menos; ?limit=diez
404La ruta o el recurso no existen/api/v1/incidencias/abc, /api/v1/no-existe
405La ruta existe, el método noDELETE /api/v1/incidencias, con Allow
422Se lee, pero los datos no valenfalta prioridad; sobra rol; título de 300 caracteres
500Fallo del servidorno debería verse nunca: si se ve, la validación no ha hecho su trabajo

Un error nunca lleva trazas, rutas de ficheros ni nombres de funciones. A quien usa bien la API no le sirven, y a quien la ataca le cuentan el lenguaje, el framework y cómo está organizado el código.

Para que todos los errores salgan así, también los que genera el framework, cada lenguaje tiene su sitio:

func problema(w http.ResponseWriter, codigo int, detalle string) {
	w.Header().Set("Content-Type", "application/problem+json")
	w.WriteHeader(codigo)
	json.NewEncoder(w).Encode(map[string]any{
		"type": "about:blank", "title": http.StatusText(codigo), "status": codigo, "detail": detalle,
	})
}

// Un patrón sin método recoge los métodos que no tienen el suyo: el 405.
mux.HandleFunc("/api/v1/incidencias", func(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Allow", "GET, POST")
	problema(w, http.StatusMethodNotAllowed, r.Method+" no se admite aquí")
})
// Y "/" recoge todo lo que no encaja con nada: el 404.
mux.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
	problema(w, http.StatusNotFound, "No existe "+r.URL.Path)
})
from http import HTTPStatus
from fastapi.exceptions import RequestValidationError
from starlette.exceptions import HTTPException as StarletteHTTPException

def problema(codigo, detalle, cabeceras=None):
    return JSONResponse(status_code=codigo, headers=cabeceras, media_type="application/problem+json",
                        content={"type": "about:blank", "title": HTTPStatus(codigo).phrase,
                                 "status": codigo, "detail": detalle})

# Los 404 y 405 que genera el propio FastAPI pasan por aquí.
@app.exception_handler(StarletteHTTPException)
async def error_http(request, exc):
    return problema(exc.status_code, str(exc.detail), exc.headers)

# Y su 422 de serie, que trae una lista técnica, también.
@app.exception_handler(RequestValidationError)
async def error_validacion(request, exc):
    return problema(422, "Datos no válidos")
import { STATUS_CODES } from "node:http";

const problema = (res, codigo, detalle) =>
  res.status(codigo).type("application/problem+json")
     .json({ type: "about:blank", title: STATUS_CODES[codigo], status: codigo, detail: detalle });

// Después de las rutas de /api/v1/incidencias: cualquier otro método, 405.
app.all("/api/v1/incidencias", (req, res) => {
  res.set("Allow", "GET, POST");
  problema(res, 405, `${req.method} no se admite aquí`);
});
// Al final de todo: lo que no ha encajado, 404; y los errores (JSON roto), 400.
app.use((req, res) => problema(res, 404, `No existe ${req.path}`));
app.use((err, req, res, next) =>
  problema(res, err.type === "entity.parse.failed" ? 400 : 500, "Petición no válida"));

Validar lo que llega

Se valida contra una lista de lo permitido, no contra una lista de lo prohibido. Para cada campo del contrato: que esté si es obligatorio, que tenga su tipo, su tamaño y sus valores. Y lo que no está en el contrato se rechaza.

Rechazar los campos desconocidos no es manía: es lo que impide que alguien cambie un dato que no debería tocar, como su propio rol. Se llama asignación masiva y lo verás en API 4.

Listas por páginas

Devolver 50 000 incidencias de golpe tarda, gasta memoria en los dos lados y deja la API a merced de quien la llame en bucle. Una lista se devuelve por páginas, y la respuesta dice cómo pedir la siguiente:

GET /api/v1/incidencias?limit=2&estado=abierta

{"datos": [{"id": 4, …}, {"id": 9, …}], "siguiente": "9"}

GET /api/v1/incidencias?limit=2&estado=abierta&cursor=9

{"datos": [{"id": 11, …}], "siguiente": null}
  • limit tiene un valor por defecto (20) y un máximo (100). Fuera de ese rango, 400.
  • El cursor marca dónde se quedó la página: aquí, el último id devuelto. La siguiente empieza después. null significa que no hay más.
  • Los filtros van en la consulta, con los mismos nombres que los campos. Un valor que no existe, 400.

¿Por qué cursor y no «página 3»? Si mientras recorres la lista alguien borra una incidencia, con números de página te saltas una; con cursor, no.

Caché: no mandar lo que ya tienes

Cada versión de un recurso lleva una etiqueta, el ETag. El cliente la guarda y, la próxima vez, pregunta si sigue valiendo:

Un 304 no lleva cuerpo: el cliente usa lo que ya tenía. En el contrato del curso el ETag es el número de versión de la incidencia entre comillas: empieza en "1" y sube con cada PUT o PATCH. Así las tres APIs del E5 dan el mismo.

Las respuestas con datos de una persona, en una API con usuarios, llevan además Cache-Control: private o no-store, para que ningún intermediario las guarde y se las dé a otro.

Cambios que no se pisan

Dos técnicos abren la incidencia 7 a la vez. Lucía la cierra; Marcos, que aún ve la versión anterior, le cambia la prioridad con un PUT. Sin más, la API se queda con lo de Marcos y el cierre de Lucía se pierde sin que nadie se entere.

La regla es corta: si una escritura trae If-Match y no coincide con el ETag actual, se responde 412 Precondition Failed y no se cambia nada. Si coincide, o no trae la cabecera, se hace el cambio y se devuelve el ETag nuevo.

Regla de la IA

Si la IA te propone un manejador de errores, comprueba con curl -i qué devuelve de verdad ante un JSON roto y una ruta que no existe, en los tres lenguajes. El framework suele tener la última palabra si no se le quita.

Comprobación

  • Distingues un 400 de un 422 y escribes un error en application/problem+json
  • Sabes dónde se cambian en cada framework los errores que genera él solo
  • Validas contra lo que permite el contrato y rechazas lo que sobra
  • Recorres una lista paginada con limit y cursor y explicas por qué cursor
  • Explicas con un ejemplo para qué sirven If-None-Match y If-Match, y qué responden
