Modelo y commits

Qué guarda git de verdad, por qué cada cambio queda sellado y cómo hacer commits que otra persona pueda leer, revisar y deshacer.

Miércoles, 1.ª horaEjercicios: E1 y E2

Git guarda fotos, no diferencias

Cada commit es una foto completa de la carpeta del proyecto, más quién la hizo, cuándo, por qué y cuál es la foto anterior (su padre). Git la guarda como cuatro tipos de objeto, y cada uno se nombra por el SHA-1 de su contenido:

ObjetoQué contiene
blobEl contenido de un fichero, sin nombre.
treeUna carpeta: nombres de ficheros y subcarpetas, cada uno con el SHA de su blob o tree.
commitEl tree raíz, el padre o padres, autor, fecha y mensaje.
tagUna etiqueta anotada: apunta a un commit con nombre, autor y mensaje propios.

Como el nombre sale del contenido, cambiar un solo byte de un commit antiguo cambia su SHA y el de todos los que vienen detrás. Es la integridad de la que hablamos en el tema de seguridad: la historia no se puede alterar sin que se note.

git cat-file -p HEAD            # el commit actual: tree, parent, author, mensaje
git cat-file -p 'HEAD^{tree}'   # su carpeta raíz
git cat-file -t <sha>           # qué tipo de objeto es

Las tres zonas

git status                 # qué ha cambiado y en qué zona está
git diff                   # trabajo frente a índice
git diff --staged          # índice frente al último commit
git add -p                 # elegir trozo a trozo qué entra
git commit -m "tipo: qué hace"   # guardar el índice como commit
git push                   # subir tus commits a GitHub (cómo funciona, en Git 3)

Commits que se entienden

Un commit atómico contiene un solo cambio lógico: se puede explicar en una línea, revisar de una vez y deshacer sin arrastrar otra cosa. El mensaje sigue Conventional Commits: tipo(ámbito): qué hace, en imperativo o descriptivo y sin punto final.

TipoCuándoEjemplo
featAlgo nuevo.feat(auditoria): inventario de la red
fixCorrige un fallo.fix(terraform): bucket sin acceso público
docsSolo documentación.docs(alcance): fechas de la prueba
choreMantenimiento que no cambia el resultado.chore: ignorar capturas .pcap

También existen refactor, test y style. Un historial así es un informe de lo que se hizo y en qué orden, y en una auditoría eso importa.

Lo que no se sube: .gitignore

Cada línea es un patrón de rutas que git no propondrá añadir. Se aplica en su carpeta y en las de debajo.

PatrónIgnora
*.logCualquier fichero que acabe en .log.
build/La carpeta build entera, esté donde esté.
/salidasSolo salidas en la carpeta del .gitignore.
!importante.logExcepción: este sí se versiona.
git check-ignore -v ruta/al/fichero   # qué regla lo ignora, y de qué fichero
git rm --cached fichero               # dejar de versionar algo que ya estaba

Un fichero que ya está versionado no se ignora aunque añadas su patrón: primero hay que sacarlo con git rm --cached. Y si contenía un secreto, sacarlo no basta: sigue en la historia. Lo veremos en Git 4.

Mirar el historial

Ninguna de estas órdenes cambia nada: solo enseñan. Los ejercicios las usan para comprobar el resultado antes de subirlo.

OrdenEnseña
git status --short -uallUna línea por fichero cambiado o sin seguimiento, también los que están dentro de carpetas nuevas.
git log --oneline --statCada commit en una línea y, debajo, los ficheros que tocó. Con --name-only, solo sus nombres.
git log --oneline --graph --allTodas las ramas como un grafo.
git show <commit>El autor, el mensaje y el diff de un commit. Con --stat, solo los ficheros.
git show <commit>:<ruta>El contenido de un fichero tal como estaba en ese commit.
git ls-tree -r --name-only <commit>Los ficheros del tree de ese commit: lo que se ve al descargarlo.

<commit> puede ser un SHA, una rama o HEAD, el commit en el que estás. Si añades -- <ruta> a git log, solo verás los commits que tocaron esa ruta.

Identidad y etiquetas

El autor de cada commit sale de tu configuración. GitHub asocia el commit a tu cuenta solo si ese correo es uno de los verificados en Settings → Emails. Si prefieres no publicar tu correo, usa la dirección …@users.noreply.github.com que aparece en esa misma página.

git config --global user.name "Tu Nombre"
git config --global user.email "un-correo-verificado@ejemplo.com"

Cada ejercicio se entrega con una etiqueta anotada. A diferencia de una ligera (git tag nombre, que es solo un puntero), una anotada es un objeto con autor, fecha y mensaje:

git tag -a entrega-fundamentos-git-e1 -m "E1 resuelto"
git push origin entrega-fundamentos-git-e1
git cat-file -t entrega-fundamentos-git-e1    # tag, no commit

Antes de etiquetar, comprueba que el ejercicio está bien. Cada vez que el docente lanza la corrección, GitHub muestra un ✓ o una ✗ junto al último commit de main en la portada de tu repositorio. Pulsa ese símbolo y abre Details en Corrector git: hay una fila por ejercicio, con los fallos que encuentra el corrector. El símbolo va en el commit que se corrigió: si subes algo después, tu último commit no lo tendrá hasta la siguiente corrección. Cuando la fila de tu ejercicio salga sin fallos, etiqueta. Una etiqueta ya subida también se puede mover a otro commit, pero eso reescribe lo publicado: lo verás en Git 3.

Regla de la IA

Pide a la IA que te proponga los mensajes de tus commits a partir de git diff --staged. Compara su propuesta con el diff antes de usarla: si menciona algo que no está en el diff, es inventado.

Comprobación

  • git cat-file -p HEAD y sabes explicar cada línea
  • Tu user.email está verificado en GitHub
  • E1 y E2 aparecen como superados en el check Corrector git y tienen su etiqueta
