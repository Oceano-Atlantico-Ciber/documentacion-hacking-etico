Remotos y reescribir historia

Cómo se sincroniza tu repositorio con GitHub y cómo dejar una rama limpia antes de compartirla, sin romper el trabajo de nadie.

Miércoles, 3.ª horaEjercicios: E5 y E6

Tu repositorio y el remoto

Tu clon es un repositorio completo. origin es solo el nombre del remoto del que clonaste, y origin/main es tu copia local de dónde estaba su main la última vez que preguntaste.

OrdenQué hace
git fetchTrae lo nuevo del remoto y actualiza origin/*. No toca tus ramas ni tus ficheros.
git pullfetch y después integra origin/main en tu rama (merge, o rebase con --rebase).
git push -u origin ramaSube la rama y la deja enlazada a su remota para los siguientes push y pull.
git branch -vvCada rama con su remota y cuántos commits va por delante o por detrás.

Un push solo se acepta si es fast-forward para el remoto. Si alguien subió antes, primero fetch e integra.

Rebase

git switch rama
git rebase main          # si hay conflicto: resuélvelo, git add, git rebase --continue
git rebase --abort       # o vuelve a como estaba

El resultado es una historia lineal, como si hubieras empezado la rama hoy. El precio es que los commits originales dejan de existir en la rama.

Rebase interactivo

git rebase -i HEAD~4 abre un editor con los cuatro últimos commits, del más antiguo al más reciente. Cambias la palabra de cada línea, guardas y git rehace la historia:

PalabraQué hace con el commit
pickLo deja como está.
rewordLo deja, pero te deja cambiar el mensaje.
squashLo funde con el anterior y te deja escribir el mensaje del conjunto.
fixupLo funde con el anterior y descarta su mensaje.
dropLo elimina.

Para retocar solo el último commit no hace falta todo esto: git commit --amend. Y para copiar un commit concreto de otra rama a la tuya, git cherry-pick <sha>.

La regla de oro

No reescribas commits que otra persona ya tiene. Si los cambias y ella los tenía, su historia y la tuya dejan de encajar. En una rama tuya que solo usas tú, reescribir está bien, pero el remoto rechazará el push porque ya no es fast-forward. Fuerza con cuidado:

git push --force-with-lease

--force-with-lease solo sobrescribe si el remoto sigue donde tú creías. Si alguien subió algo entretanto, se niega en lugar de borrarlo, que es lo que haría --force. Sobre main no se fuerza nunca.

Mover una etiqueta

Una etiqueta subida es historia publicada, como un commit: quien ya la descargó conserva la antigua. Por eso, en un proyecto real, una versión publicada no se mueve: se corrige y se publica otra. En el curso, la etiqueta de un ejercicio sí se puede mover para entregar la corrección. Cuenta la etiqueta tal como esté al cerrar el plazo; si la mueves después, la entrega queda fuera de plazo.

git tag -fa entrega-fundamentos-git-e1 -m "E1 resuelto"    # -f: la reemplaza en tu repositorio
git push --force origin entrega-fundamentos-git-e1         # y en GitHub

Para una etiqueta no existe --force-with-lease: --force la sustituye siempre, así que asegúrate de que es la etiqueta que quieres mover. Sirve para cualquier ejercicio que ya hayas entregado, también los de Git 1 y Git 2.

Práctica

E5 · Rebase y E6 · Rebase interactivo. Las dos etiquetas van sobre la punta de su rama, no sobre main.

Regla de la IA

Antes de un rebase, pide a la IA que te dibuje cómo quedará git log --graph. Después, compáralo con el real. Si no coinciden, el dibujo de la IA estaba mal, no git.

Comprobación

  • Sabes la diferencia entre fetch y pull
  • Sabes por qué un rebase cambia los SHA y cuándo no se debe hacer
