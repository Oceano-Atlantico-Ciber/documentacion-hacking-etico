01 · Git

Carpeta 01-git/. Teoría: Git 1 · Modelo y commits, Git 2 · Ramas y fusiones, Git 3 · Remotos y reescribir historia y Git 4 · Deshacer y seguridad.

Ocho ejercicios en fundamentos/git/ de tu repositorio de entregas. Cada uno empieza con preparar.py, que crea los ficheros, ramas y commits de partida a partir de tu usuario de GitHub: tu escenario es distinto del de tus compañeros. Ejecútalo desde tu repositorio, en main y sin cambios pendientes:

cd entregas-<tu-usuario>
python3 ../documentacion-hacking-etico/01-fundamentos/ejercicios/01-git/preparar.py e1

Cada ejercicio se entrega con su propia etiqueta anotada, entrega-fundamentos-git-eN, sobre el commit donde está resuelto:

git tag -a entrega-fundamentos-git-e1 -m "E1 resuelto"
git push origin entrega-fundamentos-git-e1

Cuenta la primera etiqueta que subas. Moverla o borrarla después no cambia la entrega. Antes de etiquetar, sube tu trabajo y mira el resultado provisional: en GitHub, junto al último commit de main, aparece el check Corrector git con una fila por ejercicio. Se actualiza cuando el docente lanza la corrección. Cuando tu ejercicio salga sin fallos, etiqueta.

Ej.Qué hacesEtiqueta sobre

E1 · Identidad y commits atómicos

  1. Comprueba que git config user.email es uno de los correos verificados de tu cuenta de GitHub (Settings → Emails). Si no, GitHub no asocia tus commits a tu cuenta y el ejercicio no cuenta.
  2. preparar.py e1 deja tres ficheros sin versionar en fundamentos/git/e1/.
  3. Haz tres commits, cada uno con un solo fichero, con mensajes Conventional Commits: docs(e1): objetivo de la auditoría.
  4. Sube main y etiqueta.

E2 · .gitignore

  1. preparar.py e2 deja en fundamentos/git/e2/ el programa app.py y lo que genera al ejecutarse: build/, depuracion.log y .env.
  2. Crea fundamentos/git/e2/.gitignore para que git status solo proponga app.py y el propio .gitignore. Compruébalo con git check-ignore -v.
  3. Commit, push y etiqueta. Si alguno de los ignorados llega a un commit, aunque lo borres después, el ejercicio falla.

E3 · Fusiones

  1. preparar.py e3 crea las ramas git/e3-ff y git/e3-noff, con un commit cada una.
  2. Integra git/e3-ff en main con fast-forward, sin commit de merge.
  3. Integra git/e3-noff con un commit de merge (--no-ff).
  4. Sube main y etiqueta.

E4 · Conflicto

  1. preparar.py e4 añade a main el inventario fundamentos/git/e4/puertos.txt y crea git/e4-a y git/e4-b: dos auditores que han encontrado un puerto más cada uno.
  2. Integra las dos ramas en main. La segunda dará conflicto.
  3. Regla: el inventario final tiene todas las líneas de las dos ramas, una por puerto, ordenadas por número de puerto y sin marcadores de conflicto.
  4. Termina el merge, sube main y etiqueta.

E5 · Rebase

  1. preparar.py e5 crea git/e5-feature con dos commits y, después, añade un commit a main, como si lo hubiera subido un compañero.
  2. Rebasa git/e5-feature sobre main. Sin merges: la rama debe quedar lineal encima de main.
  3. Sube main y la rama (git push -u origin git/e5-feature, o --force-with-lease si ya la habías subido) y etiqueta la punta de la rama.

E6 · Rebase interactivo

  1. preparar.py e6 crea git/e6-wip con cuatro commits wip(e6): paso N que van escribiendo un informe.
  2. Con git rebase -i, fúndelos en un único commit con el mensaje exacto docs(e6): informe de alcance.
  3. Sube la rama y etiqueta su punta.

E7 · Revert

  1. preparar.py e7 añade tres commits a main. El segundo activa el modo depuración del servidor por error. Sube main: a partir de ahí ese commit es público.
  2. Deshaz ese commit sin reescribir la historia: el commit erróneo debe seguir en ella y el tercero también.
  3. Sube main y etiqueta.

E8 · Secreto filtrado

  1. preparar.py e8 crea git/e8-app. En algún commit alguien subió un .env con una clave de API, y después lo borró.
  2. Sube la rama tal cual: git push -u origin git/e8-app. Simula la filtración real.
  3. Encuentra el commit que introdujo la clave (git log -p -S) y apunta su SHA completo.
  4. Purga el .env de toda la historia de la rama: 
    pip install git-filter-repo
git filter-repo --refs git/e8-app --path fundamentos/git/e8/.env --invert-paths --force
  5. En la rama, guarda el SHA del paso 3 en fundamentos/git/e8/hallazgo.txt y haz commit. Sube con --force-with-lease y etiqueta.
  6. Comprueba en GitHub la dirección …/commit/<SHA>. ¿Sigue ahí la clave? ¿Qué habría que hacer con ella en un caso real?

Cómo se valora

  • Cada ejercicio vale lo mismo y se corrige de forma automática desde su etiqueta: estructura del historial (padres de los merges, commits por rama, conflicto real) y contenido de los ficheros.
  • Las fechas de los commits no cuentan. Cuenta la hora a la que subiste la etiqueta, antes del cierre del bloque.

Empresa con Terraform

Carpeta empresa-con-terraform/. Enunciado: La empresa en Floci. Cómo montar el laboratorio paso a paso: Puesta en marcha.

  1. Copia plantilla-alumno/alcance.html a fundamentos/alcance.html y rellénalo: objetivo (la cuenta emulada en tu portátil), qué se permite, quién autoriza (el docente) y fechas.
  2. Copia la carpeta del ejercicio a fundamentos/ de tu repositorio y levanta la nube: docker compose up -d floci.
  3. Pasa Trivy y guarda la salida: docker compose run --rm trivy | tee fundamentos/trivy-antes.txt.
  4. Por cada aviso, pide a la IA que explique qué significa y qué cambio propone, compruébalo en la documentación del recurso de Terraform y aplícalo. Repite Trivy hasta que no quede ningún aviso alto ni crítico: fundamentos/trivy-despues.txt.
  5. Despliega en Floci y comprueba con la CLI de AWS que la empresa existe: 
    docker compose run --rm terraform init
docker compose run --rm terraform apply
docker compose run --rm aws s3 ls
docker compose run --rm aws iam list-users

Cómo se valora

  • Trivy sin avisos altos ni críticos sobre el Terraform entregado.
  • El Terraform sigue desplegando sin errores. Corregir no es borrar: la empresa necesita su bucket, su usuario y su cortafuegos.
  • Commits a lo largo del trabajo, no un volcado final.

Mini auditoría

  1. Levanta el laboratorio (docker compose up -d) y vuelve a desplegar el Terraform corregido de Empresa con Terraform contra este Floci, para que la cuenta tenga contenido.
  2. Reconocimiento: qué equipos hay en la red. docker compose run --rm auditor -sn 172.28.0.0/24.
  3. Enumeración: qué servicio y versión hay en cada uno (-sV sobre las tres direcciones) y qué recursos tiene la cuenta (aws s3 ls, aws iam list-users, aws ec2 describe-security-groups). Todo a fundamentos/inventario/red.txt y fundamentos/inventario/nube.txt.
  4. Mira la web con curl desde el auditor (portada y robots.txt) y anota qué descubres.
  5. Detección: python3 etiquetar.py resume las alertas de Suricata por fase y por origen. Guarda la salida en fundamentos/alertas/resumen.txt.
  6. Escribe al menos una regla propia en suricata/local.rules (sid a partir de 1000100) que detecte algo que hayas hecho y que no saltara, reinicia Suricata y comprueba que salta. Entrega el fichero en fundamentos/alertas/local.rules.
